====================================================================
一、先用大白话说明 1.00 最终要做什么
====================================================================

Cherry Gateway 是一个运行在用户 Windows 电脑上的本地 AI 网关。Cherry Studio
和其他客户端只看到一个本地 API 地址和一个本地客户端 Key；真正的中转站地址、
中转站 Key、请求线路和思考强度由网关在本机管理。

1. 本地网关是第一优先级
   没有网络、GitHub 不能访问、同步授权过期时，本地转发仍然可以工作。云同步
   只是备份和复制，不是网关运行的前置条件。

2. GitHub 是默认云同步渠道
   一个用户默认使用一个私有仓库和一个固定 Release。同步文件放在 Release
   附件中，不把每 30 分钟的统计写成普通 Git 提交。

3. 云端不保存客户端 Key
   客户端 Key 是给本机 Cherry Studio 使用的本地凭证。云端最多保存客户端
   Key 的名称、绑定线路 ID、状态和摘要，完整客户端 Key 只留在本机。

4. 中转站敏感信息单独加密
   API URL、认证方式、自定义 Header、代理/TLS 等决定“真实 Key 发往哪里”的
   安全连接配置，和上游 API Key 一起放在加密 vault 中。不能只保护 API Key，
   却把 Base URL 作为普通可修改配置上传。

5. 使用量永久累计，但明细可以清理
   永久总账不受时间限制。请求明细超过 50 MiB 后按最早记录清理至约 45 MiB；
   清理明细不能减少永久请求数、Token、成功失败数和缓存统计。

6. 多设备同步不是“最后一个上传的人覆盖一切”
   使用记录按唯一 eventId 去重，统计按设备和设备纪元计数；配置删除产生墓碑；
   同字段冲突必须提示用户，不能静默覆盖。

7. 网关重置不是云端重置
   网关重置只重新选择本机端口并重新启动监听器，用于解决端口冲突。它不删线路、
   不删客户端 Key、不删统计、不删云端数据、不改变 datasetId。

二、5.6-sol 审查意见的最终取舍
====================================================================

A. 1.00 必须实现，作为发布阻断项
--------------------------------------------------------------------
1. Offline First：本地先落盘，云同步失败不阻塞网关。
2. 本地待同步队列和崩溃恢复。
3. datasetId、deviceId、deviceEpoch、eventId、sequence、syncId。
4. 一次只允许一个主同步提供商；GitHub 为默认主提供商，其他云盘不能同时
   作为三个互相覆盖的“权威数据库”。
5. Release Asset 不可变代、manifest 最后提交、上传前校验、旧代保留和垃圾
   清理保护。
6. usage 使用不可变增量分片，不再每 30 分钟反复覆盖一个持续变大的文件。
7. 每个 deviceId + deviceEpoch 使用 G-Counter 计算永久总账，禁止简单地把
   多设备 summary 相加后反复累计。
8. 删除配置产生 tombstone，防止离线设备重新上传已删除线路或 Key。
9. 安全连接配置和上游 API Key 一起进入加密 vault。
10. DEK/KEK 信封加密、AES-256-GCM、Argon2id、恢复码、keyEpoch 和 vaultRevision。
11. 错误密码不能生成空 vault，也不能覆盖当前正确 vault。
12. 云端恢复必须先下载、校验、解密、解析、预览，再合并；不直接覆盖本地。
13. GitHub 的 401、403、404、409、422、429、5xx、超时和断网均有可恢复状态。
14. 测试必须覆盖多设备竞态、同步中断、损坏文件、云端删除、授权撤销和篡改。
15. EXE 不依赖用户单独安装 Node.js 或 SQLite，正式安装包要自带运行环境。

B. 1.00 推荐实现，但可用功能开关或分阶段落地
--------------------------------------------------------------------
1. Google Drive appDataFolder 适配器。
2. OneDrive approot 适配器。
3. 剪贴板复制后 30 至 60 秒自动清空。
4. 无签名安装包的 SmartScreen 说明，以及以后代码签名的发布流程。
5. 更细的同步诊断界面和导出脱敏日志。

最终决定：1.00 先把 GitHub 主流程做完整并通过全部 P0/P1；Google Drive 和
OneDrive 只在不影响 GitHub、本地网关和安全模型的前提下作为可选适配器。没有
配置这些服务时，界面不显示阻塞性错误，也不要求用户购买会员。

C. 明确暂不做，防止过度设计
--------------------------------------------------------------------
1. Kubernetes、Redis、外部数据库、自建服务器或复杂分布式协调服务。
2. 让 GitHub、Google Drive、OneDrive 三者同时成为互相写入的多主数据库。
3. 自动 force push、自动重写用户 Git 历史、自动删除用户代码仓库提交。
4. 公开云端中心账户、服务端计费系统、用户行为遥测。
5. LAN 暴露、本地 API 默认监听 0.0.0.0、所谓“本地路由”独立产品模块。
6. 为了看起来复杂而把所有普通配置强制迁移到数据库。

====================================================================
四、最终产品边界
====================================================================

1. 网关业务
--------------------------------------------------------------------
- 监听地址默认为 127.0.0.1。
- 端口在 20000 至 48999 的 29,000 个候选端口中安全随机选择可用端口。
- 支持 OpenAI 兼容的 Responses 和 Chat Completions。
- 支持流式和非流式响应。
- 支持 /v1/models，并且只返回客户端 Key 所绑定线路的模型。
- 客户端 Key 只能绑定一条线路。
- 一个客户端 Key 可停用、启用、编辑和永久删除。
- 删除后该 Key 不能再认证；删除记录不能让旧 Key 从同步或缓存中复活。
- 思考强度固定为 low、medium、high、xhigh、max 五档。
- 网关真实透传请求字段；上游不支持某档时显示上游实际错误，不静默改成 medium。

2. 云同步
--------------------------------------------------------------------
- GitHub 是默认同步渠道。
- 开启同步、关闭同步、软件启动、软件退出、手动同步、恢复、账户变更、密码
  变更和安全连接配置变更属于重大事件，必须触发一次同步尝试。
- 普通同步默认每 30 分钟一次，只有本地有变化时才上传。
- 同步失败只进入队列，不删除本地数据，不停止网关。
- 关闭同步默认只关闭自动同步，不删除云端数据。
- “删除云端备份”是独立按钮，必须明确确认；删除后也不能声称已经抹除服务商
  所有内部备份副本。

3. 统计
--------------------------------------------------------------------
- 永久累计没有时间限制。
- 时间范围支持 24 小时、7 天、30 天、90 天、半年。
- 明细超过 50 MiB 后清理最早记录至约 45 MiB；不按条数或时间清理。
- 支持输入、输出、缓存读取、缓存创建、总 Token、请求数、成功失败、成本
  （若上游提供且用户配置了计费信息）、TTFT 和总耗时。
- 上游没有返回 usage 时记录请求、状态和耗时，Token 显示 0，不根据文字长度伪造。

4. 明确不包含
--------------------------------------------------------------------
- 不上传提示词、回答、消息数组、系统提示词、Cookie、完整 IP。
- 不把客户端 Key 上传到任何云端。
- 不把本地网关暴露到局域网，除非以后用户明确打开独立的 LAN 选项。
- 不增加“本地路由”独立模块；线路页就是网关使用的中转线路管理。

单实例原则
--------------------------------------------------------------------
1. Electron 使用 requestSingleInstanceLock，第二次启动只唤醒已有窗口。
2. 只有主实例能启动网关和打开 SQLite 写连接。
3. 第二实例不能启动第二个网关、不能创建第二个 deviceEpoch、不能覆盖数据。
4. renderer 任何写入都经由 IPC，在主进程中执行参数校验和事务。

六、本地文件、数据库和数据分区
====================================================================

正式运行数据目录
--------------------------------------------------------------------

```text
<软件 EXE 所在目录>\data\gateway-data\
├── config.json                 普通配置，不含真实上游 Key
├── vault.enc                   本机加密安全连接配置，可选云端加密副本
├── usage.db                    SQLite 使用总账、明细、队列和墓碑
├── usage.db-wal                SQLite 运行时 WAL 文件
├── usage.db-shm                SQLite 运行时共享内存文件
├── device.json                 deviceId、deviceEpoch、安装实例信息
├── sync-state.json             当前 Provider、datasetId、远端指纹和调度状态
├── migration-state.json        迁移进度和回滚信息
├── backups\                    迁移前及危险操作前的本机备份
└── logs\                       脱敏日志；默认只保留有限大小
```

普通 config.json 只保存
--------------------------------------------------------------------
- schemaVersion、configRevision。
- routeId、线路显示名称、启用状态、非敏感模型目录元数据。
- 最近检测状态、延迟、错误摘要和检测时间。
- clientId、客户端 Key 名称、绑定 routeId、思考强度、启用状态、创建时间、
  nameCustomized。
- UI 语言、开机自启、启动隐藏、关闭进托盘。
- 同步开关、默认 Provider、触发设置和仅用于显示的账户摘要。
- GitHub 仓库名称、Release ID、datasetId 等标识信息；授权 Token 不放这里。

必须进入 vault.enc 的字段
--------------------------------------------------------------------
- 上游 API Key。
- Base URL / API URL。
- 认证方式、Authorization 模板、自定义 Header。
- 代理、TLS 验证、证书指纹或其他会改变真实请求目的地的安全参数。
- Provider 的敏感连接凭据（不包括已经进入 Windows 安全存储的 OAuth Token）。

为什么 Base URL 也算敏感
--------------------------------------------------------------------
如果云端配置被修改为 localhost、169.254.169.254、内网地址或攻击者域名，
程序可能把真实 Key 发往错误地点。因此恢复云端配置时，Base URL、代理、TLS
和认证方式必须按安全连接配置处理，并在发生变化时要求用户确认，不能在后台
悄悄生效。

SQLite 数据库用途
--------------------------------------------------------------------
SQLite 只用于需要事务和可靠增量的内容，不强制把所有设置搬进数据库。

```text
usage_events
  每请求一行，不含消息正文和任何密钥。

usage_counters
  每个 deviceId + deviceEpoch 的永久计数器。

outbox
  本地已落盘但尚未确认进入远端 manifest 的事件/对象。

tombstones
  线路、客户端 Key 等对象被删除后的墓碑。

sync_runs
  每次同步的开始、结束、状态、错误分类、上传代数和脱敏摘要。

schema_meta
  数据库 schema 版本和迁移记录。
```

SQLite 运行规则
--------------------------------------------------------------------
1. 启用 WAL、foreign_keys、busy_timeout。
2. 单个主进程持有写连接，所有事件写入使用事务。
3. “请求结束”和“usage 事件 + counter + outbox”必须在同一事务中提交。
4. 网关响应已经发出但统计写入失败时，必须记录可见的“统计待修复”状态，
   不能伪装为已统计。
5. 不直接复制正在写入的 db 文件作为云端对象；上传前执行 checkpoint，并从
   只读快照/导出分片生成云端文件。
6. 迁移前复制本地数据到 backups，并且验证备份可读后再改变 schema。

====================================================================
七、编号、时间和数据格式
====================================================================

1. datasetId：同步宇宙编号
--------------------------------------------------------------------
datasetId 表示“这一组云端数据属于哪个同步集合”。更换 GitHub 账户、仓库、
Release 或从另一台设备恢复时，必须检查 datasetId。不同 datasetId 不能被程序
静默合并。

示例：

```text
ds_01995f2c-7f5a-7b21-a8d2-6dfc50f4a901
```

2. deviceId：安装设备编号
--------------------------------------------------------------------
- 首次运行随机生成 UUID，不使用 MAC、CPU、硬盘序列号等硬件指纹。
- 卸载重装或用户明确“作为新设备”时生成新 deviceId。
- 设备复制数据目录到另一台电脑时，必须检测并创建新的 deviceId，不能让
  两台设备共用同一个设备身份。

3. deviceEpoch：设备纪元
--------------------------------------------------------------------
- 每当检测到数据目录克隆、sequence 回退或本地计数器恢复异常时递增。
- 永久计数使用 deviceId + deviceEpoch 作为独立计数来源。
- 这样可以避免克隆设备继续使用相同 sequence 导致计数丢失或重复。

4. eventId：请求事件唯一编号
--------------------------------------------------------------------
- 使用 UUIDv7 或同等级别的 128 位随机唯一值。
- eventId 是去重依据，不能用短名称、时间戳或 sequence 替代。

5. sequence：设备本地递增序号
--------------------------------------------------------------------
- 每个 deviceId + deviceEpoch 独立递增。
- 用于发现断号和诊断，不作为全局唯一键。

6. syncId：一次同步操作编号
--------------------------------------------------------------------
- 每次同步生成新值，用于 asset 文件名、日志关联和冲突诊断。

7. routeId、clientId
--------------------------------------------------------------------
- 创建时随机生成，改名不变。
- routeId 用来绑定线路，clientId 用来绑定客户端凭证。
- 删除后写入 tombstone，避免旧设备重新上传。

8. generation：远端提交代数
--------------------------------------------------------------------
- 表示一个已提交的同步包的新旧，不表示 Git 提交或软件版本。
- 新 generation 必须记录 parentGeneration 和 parentManifestSha256。

9. configRevision
--------------------------------------------------------------------
- 配置逻辑版本，不直接依赖电脑时间。
- 推荐使用 {counter, deviceId} 形式比较并发修改。

10. 时间
--------------------------------------------------------------------
- 存储和协议统一使用 UTC ISO-8601，例如 2026-09-16T10:30:00.000Z。
- 界面默认显示 UTC+8，也允许显示用户系统时区。
- 时间只辅助展示和排序，不能仅凭本机时间决定云端覆盖本地。

====================================================================
九、云端 Release Asset 最终协议
====================================================================

GitHub 云端布局
--------------------------------------------------------------------
1. 默认每个账户一个专用私有仓库。
2. 默认一个固定 Release，例如固定 tag `cherry-sync`，不每次创建新 Release。
3. 文件使用 ASCII 文件名，便于 GitHub API、Windows 和多云适配器统一处理。
4. 普通仓库不保存高频同步数据，不生成每 30 分钟一次的代码提交。
5. 1.00 不自动重写 Git 历史，也不承诺服务商内部缓存会物理抹除。

对象命名
--------------------------------------------------------------------

```text
manifest-g000042-s<syncId>.json
summary-g000042-s<syncId>.json.gz
config-g000042-s<syncId>.json.gz
vault-g000042-s<syncId>.enc
usage-<deviceId>-e<deviceEpoch>-202609-s000001-e000245-<syncId>.jsonl.gz
```

说明
--------------------------------------------------------------------
- `g000042` 是 generation。
- `s<syncId>` 防止多设备同一代同名覆盖。
- usage 是按设备、设备纪元、月份和 sequence 范围命名的不可变增量分片。
- 每次同步只上传新的 usage 分片和新的汇总引用，不覆盖持续变大的总文件。
- 一个分片达到约 16 至 20 MiB 压缩后，或同一设备同月积累 8 至 16 个分片，
  进入 compact：先生成新的封存 shard，验证后才清理被完全引用的旧分片。
- 单个压缩对象目标不超过 20 MiB，硬限制 24 MiB；超出必须拆分，不能强行上传。

manifest 最终格式
--------------------------------------------------------------------

```json
{
  "format": "cherry-gateway-sync",
  "schemaVersion": 1,
  "minReaderVersion": "1.00",
  "minWriterVersion": "1.00",
  "datasetId": "ds_...",
  "syncId": "sync_...",
  "generation": 42,
  "parentGeneration": 41,
  "parentManifestSha256": "...",
  "writerDeviceId": "dev_...",
  "writerDeviceEpoch": 1,
  "createdAtUtc": "2026-09-16T10:30:00.000Z",
  "displayTimezone": "Asia/Shanghai",
  "state": "committed",
  "configRevision": {"counter": 18, "deviceId": "dev_..."},
  "keyEpoch": 2,
  "vaultRevision": 9,
  "files": [
    {"type":"summary","assetName":"...","sha256":"...","size":1234},
    {"type":"config","assetName":"...","sha256":"...","size":2345},
    {"type":"vault","assetName":"...","sha256":"...","size":3456},
    {"type":"usage-segment","assetName":"...","sha256":"...","size":4567}
  ],
  "tombstones": [
    {"objectType":"clientKey","objectId":"client_...","deletedRevision":"..."}
  ],
  "retention": {
    "detailQuotaBytes": 5368709120,
    "detailHardLimitBytes": 8589934592,
    "prunedBeforeUtc": null
  }
}
```

manifest 规则
--------------------------------------------------------------------
1. 只有 state=committed 的 manifest 才是可用提交。
2. 数据文件全部上传、重新读取、大小校验和 SHA-256 校验通过后，manifest 才能
   上传。manifest 永远最后上传。
3. manifest 包含所有被当前代引用的对象；未被引用的资产不能当作当前数据。
4. 下载多个 manifest 时，先检查 datasetId、schema、哈希、generation 和 parent 链；
   不能只按文件修改时间选择。
5. 新设备遇到 minReaderVersion 高于自身版本时停止写入并提示升级，不能读一半
   后用旧格式覆盖新数据。

一次提交的安全顺序
--------------------------------------------------------------------

```text
本地事务提交 usage/config/tombstone
        ↓
生成不可变 usage 分片、summary、config、vault
        ↓
压缩；安全对象按协议加密
        ↓
计算 SHA-256、大小和类型
        ↓
再次读取远端 manifest，确认 datasetId 和父代
        ↓
上传所有数据资产
        ↓
逐个读取远端资产并校验大小、哈希和 schema
        ↓
上传新的 committed manifest（最后一步）
        ↓
确认 manifest 可下载且引用全部完整
        ↓
旧代进入保留/清理候选，不得立即删除
```

并发设备规则
--------------------------------------------------------------------
1. 同一进程使用本地同步锁，同一时间只能有一个同步任务。
2. 多台设备分别读取 parentGeneration 41 后，都使用唯一 syncId 上传候选数据。
3. 如果另一台设备先提交 generation 42，后提交设备重新读取最新 manifest，
   用 eventId、G-Counter、配置三方合并生成 generation 43。
4. 失败或未被 manifest 引用的资产属于 orphan，不可当成有效数据。
5. 同一字段同时修改属于冲突；不同字段修改自动合并。

垃圾清理 mark-and-sweep
--------------------------------------------------------------------
1. 先读取并验证当前 committed manifest。
2. 标记当前代、上一个代和最近三个可回滚代引用的全部资产。
3. 额外保留孤儿资产至少 24 小时，防止上传完成但 manifest 确认延迟时误删。
4. 清理未标记、超过宽限期且不属于当前/回滚代的对象。
5. 清理失败不影响网关和下次同步；清理不是提交成功的前置条件。
6. Release 资产接近 800 个时提醒；达到 900 个时停止继续制造无意义历史，
   先执行安全清理。不得等到服务商硬限制才处理。
7. 永远先有完整新代，再清理旧代；禁止先删旧代再上传新代。

====================================================================
十、压缩、加密和密钥保护
====================================================================

压缩顺序
--------------------------------------------------------------------
```text
结构化 JSON / JSONL
        ↓
字段长度和 schema 校验
        ↓
gzip 压缩
        ↓
需要保密的对象再进行 AES-256-GCM 加密
        ↓
SHA-256、大小和类型登记到 manifest
```

加密范围
--------------------------------------------------------------------
- summary 和使用统计不含秘密，仍需 gzip 和哈希校验。
- config 只含普通配置，仍需 gzip 和哈希校验。
- vault 是压缩后加密的安全连接配置。
- 客户端 Key 完整值不进任何云端对象，无论是否加密。

信封加密最终方案
--------------------------------------------------------------------
1. 随机生成 256 位 DEK（Data Encryption Key）。
2. 使用 DEK + 12 字节新随机 nonce 进行 AES-256-GCM 加密压缩后的 vault。
3. 用户密码通过 Argon2id 派生 KEK-password，用来包裹 DEK。
4. 恢复码通过独立 salt 和 Argon2id 派生 KEK-recovery，用来包裹同一个 DEK。
5. 云端只保存 KDF 参数、salt、nonce、wrapped DEK、ciphertext、authTag、
   datasetId、schemaVersion、keyEpoch 和 vaultRevision。
6. 密码、恢复码、明文 DEK 和明文上游 Key 永远不上云。
7. AES-GCM 的 AAD 必须包含 datasetId、schemaVersion、对象类型、keyEpoch、
   vaultRevision，跨数据集复制或篡改时解密失败。
8. 每次加密必须使用新的随机 nonce；禁止固定 nonce。

版本和密码操作
--------------------------------------------------------------------
- keyEpoch 只在 DEK 真正轮换时递增。
- vaultRevision 在密码重新包裹、恢复码轮换或安全配置变更时递增。
- 修改密码默认只重新包裹 DEK，不必重新加密整个 vault。
- 用户恢复成功后必须提示轮换恢复码；是否一次性使用由产品设置明确说明，
  默认按一次性恢复处理。
- 恢复码至少 128 位熵，完整内容只显示一次，提供复制/保存提示但不写日志。
- 错误密码不能覆盖当前 vault、不能生成空配置、不能把本机数据置空。
- 旧设备的低 keyEpoch 数据不能覆盖新 keyEpoch 数据。

本地 Token 和客户端 Key
--------------------------------------------------------------------
- GitHub/Google/OneDrive OAuth Token 放 Windows Credential Manager 或 DPAPI。
- DPAPI 只解决本机保护，不声称可以跨电脑自动解密。
- 客户端 Key 本地也使用系统安全存储或本机加密存储；复制动作只能返回对应
  客户端 Key，绝不能返回上游 API Key。
- 复制按钮属于本地高频操作，建议复制成功后 30 至 60 秒自动清理剪贴板，并
  在设置中说明这不是对其他剪贴板监控软件的绝对防护。

日志脱敏
--------------------------------------------------------------------
所有日志、HTTP 调试、错误摘要和崩溃信息统一经过 redactSecret()：
- Authorization、Bearer、api_key、token、password、recovery、ciphertext、
  完整客户端 Key 和上游 Key 均替换为 [REDACTED]。
- URL 中的 query token、Header 值和 Cookie 统一清理。
- 日志只保存 routeId、model、status、耗时、错误类别和 syncId 等必要信息。

====================================================================
十一、同步提供商、账户和错误状态
====================================================================

Provider 抽象接口
--------------------------------------------------------------------

```text
authenticate()
refreshAuth()
getIdentity()
getQuota()
verifyConnection()
listObjects()
getObjectMetadata(objectId)
downloadObject(objectId)
uploadObject(objectName, bytes, metadata)
deleteObject(objectId)
logout()
```

最终权威关系
--------------------------------------------------------------------
1. 同一 datasetId 同一时间只能有一个 Active Sync Provider。
2. GitHub 默认是 Active Provider。
3. Google Drive/OneDrive 可以是用户主动选择的镜像/备份 Provider，但不能在
   没有合并协议的情况下同时写同一套数据并互相覆盖。
4. 切换 Provider 或 GitHub 账户时，读取 providerAccountId 和 datasetId；发现
   账户不同，必须让用户选择“创建新备份、恢复新数据、迁移当前数据”，不能自动
   把两套数据直接合并。
5. 任何 Provider 失败都只能改变同步状态，不能改变网关在线状态。

GitHub 权限和登录
--------------------------------------------------------------------
1. 桌面程序使用 Device Flow 或 GitHub App 的用户授权流程，不把客户端 Secret
   硬编码到 EXE。
2. 如果自动创建私有仓库需要较宽权限，授权前明确说明用途、范围和撤销方法。
3. 最小权限优先；未来可增加“用户手动准备私有仓库”的低权限模式。
4. 每次同步前检查仓库仍为 private。发现 public 时立即暂停上传并警告用户。
5. 用户密码不进入 Cherry Gateway；只保存系统安全存储中的授权引用。
6. 更新检查只读取指定公开项目的最新 Release，不上传用户数据，不自动替换 EXE。

错误分类和状态机
--------------------------------------------------------------------

```text
DISABLED           用户关闭自动同步
IDLE               已连接且没有待同步变化
DIRTY              本地有待同步变化
SYNCING            正在读取、合并、上传或验证
PENDING_NETWORK    断网、超时或等待退避
AUTH_REQUIRED      Token 过期、撤销或权限不足
CONFLICT           需要用户处理配置冲突
ERROR_RECOVERABLE  可重试的 API、校验或服务端错误
ERROR_FATAL        schema 不兼容、严重篡改或无法安全解密
```

重试规则
--------------------------------------------------------------------
- 401：尝试刷新授权；刷新失败转 AUTH_REQUIRED。
- 403：检查权限、public 仓库和限流信息，不无限重试。
- 404：区分仓库/Release/Asset 被删，进入恢复向导。
- 409/412：重新读取 manifest，按并发合并流程处理。
- 422：记录可读的参数/对象错误，修正前不重复提交。
- 429：读取 Retry-After 和 rate limit headers，按服务端建议等待。
- 500/502/503/504/网络超时：指数退避 + 随机抖动，设置最大次数和下次时间。
- 所有重试都必须有上限；关闭窗口和退出流程不能无限等待。

====================================================================
十二、同步触发、关闭和睡眠恢复
====================================================================

普通同步
--------------------------------------------------------------------
- 默认每 30 分钟检查一次。
- 没有 dirty 状态时只做轻量状态检查，不上传。
- 超过 100 条新事件或约 1 MiB 待同步数据时可以提前触发。
- 8 次快速编辑在 10 秒内合并为一次任务，不产生 8 个云端代数。

重大事件
--------------------------------------------------------------------
以下事件必须立即发起一次同步尝试：
1. 用户开启同步。
2. 用户关闭同步。
3. 软件启动并完成本地数据读取。
4. 用户点击立即同步。
5. 正常退出前。
6. GitHub 账户、仓库或 Active Provider 变更。
7. 远端恢复完成。
8. 加密密码/恢复码变更。
9. Base URL、认证方式、代理、TLS 或上游 Key 等安全连接配置变更。

开启同步
--------------------------------------------------------------------
1. 本地先读取并备份当前状态。
2. 拉取远端 committed manifest。
3. 校验 datasetId、版本和全部引用资产。
4. 生成 Merge Preview；没有冲突才合并。
5. 生成并提交新代。
6. 提交成功后开关显示“已开启”，失败则保留本地队列并显示具体原因。

关闭同步
--------------------------------------------------------------------
1. 立即尝试一次同步。
2. 成功：关闭自动同步，云端数据保留。
3. 失败：可以关闭自动同步，但必须显示“有数据尚未上传”，本地队列保留。
4. 关闭同步不删除云端、不删除本机历史、不改变 datasetId。

软件退出
--------------------------------------------------------------------
- 正常退出时给同步任务一个有限时间窗口。
- 同步成功再退出；超时则保存队列并退出，不阻塞用户太久。
- 关闭窗口默认进托盘，不等同于退出。
- 断电、任务管理器强制结束和崩溃无法保证最后一次上传，但本地事件必须已
  先事务提交，下次启动继续上传。

睡眠/唤醒
--------------------------------------------------------------------
- 从睡眠恢复后不补跑所有错过的 30 分钟任务。
- 恢复后执行一次同步，成功后重新开始 30 分钟计时。

====================================================================
十三、恢复、合并、删除和云端损坏处理
====================================================================

下载处理顺序（不可调换）
--------------------------------------------------------------------
```text
限制单文件大小和总解压大小
        ↓
读取原始字节并计算 SHA-256
        ↓
检查文件类型、文件名和 schemaVersion
        ↓
如为 vault，先验证 AEAD 并解密
        ↓
限界 gzip 解压，防止 gzip bomb
        ↓
JSON/JSONL schema 校验和字段长度校验
        ↓
业务解析、eventId 去重、冲突预览
        ↓
本地 SQLite/config 原子事务提交
```

恢复规则
--------------------------------------------------------------------
1. 永远不能把下载文件直接覆盖到正式 config.json 或 usage.db。
2. 先在临时目录完成所有校验，再展示 Merge Preview。
3. 本地尚未上传的 events 必须保留。
4. usage 按 eventId 合并；重复事件只保留一份。
5. 配置按 objectId 和 Base/Local/Remote 三方版本合并。
6. 不同字段修改自动合并；同字段修改提示用户选择本机、云端或手动处理。
7. 删除和修改冲突时，显示“删除 vs 修改”并要求用户确认。
8. vault 需要正确密码/恢复码和 keyEpoch 校验，解密失败时不改变当前本机 vault。
9. 全部完成后才在一个本地事务中提交，并保留恢复前备份。

删除墓碑
--------------------------------------------------------------------
- 删除线路或客户端 Key 时写入 tombstone。
- tombstone 至少随当前代和最近三个回滚代保留。
- 离线设备下载墓碑后必须删除或停用本地对象，不能重新上传旧对象。
- tombstone 过期清理必须有明确保留期限和代数依据，不能按“本机看不到了”立即删。

云端对象被用户手动删除
--------------------------------------------------------------------
- manifest 被删：进入“远端数据不完整”向导，可选择用本地队列创建新代。
- usage 分片被删：若 manifest 仍引用，显示校验失败，不静默减少永久总账。
- vault 被删：保留本机 vault，提示重新初始化安全备份，不清空本地 Key。
- Release 被删：提示重新创建固定 Release；创建前检查 datasetId 和用户确认。
- 私有仓库被删：不自动在陌生仓库重建并上传，先提示用户选择新仓库/新 datasetId。

====================================================================
十四、线路、客户端 Key、思考强度和网关重置
====================================================================

线路
--------------------------------------------------------------------
- routeId 创建后不变；显示名称可编辑。
- 线路保存后可单独“检测线路/同步模型”。
- 检测访问该线路的 /v1/models，记录状态、耗时、时间和脱敏错误摘要。
- 没有真实检测成功记录的线路显示“未检测”，不能伪造在线。
- 删除线路前检查绑定的客户端 Key；有绑定时先改绑或删除 Key。

客户端 Key
--------------------------------------------------------------------
- 创建时必须绑定一条有效线路和一个思考强度。
- 默认名称等于绑定线路名称。
- 用户未自定义名称时，线路名称变化会同步客户端 Key 名称。
- 用户手动改名后记录 nameCustomized=true，之后不再跟随线路名。
- 首次创建完成后显示完整 Key，并提供复制 Key；列表只显示摘要。
- 卡片首行提供“复制 Key”和“复制本地 API 地址”两个高频按钮。
- 危险操作停用、启用、永久删除放在独立操作区，不能和复制按钮混在一起。
- 历史 Key 如果只有摘要没有密文，必须显示“不可恢复”，只能在用户确认后重新生成。
- 永久删除后从认证缓存、列表、本地有效 Key 集合和同步墓碑中处理干净。

思考强度
--------------------------------------------------------------------
固定五档：

```text
low
medium
high
xhigh
max
```

- Responses 请求写 reasoning.effort。
- Chat Completions 请求写 reasoning_effort。
- 客户端 Key 设置优先于全局默认设置。
- 上游实际不支持某档时，保留用户选择并显示上游原始错误；不能偷偷降级成 medium。
- 测试必须检查客户端 UI、网关入站、上游出站和中转站记录四个层面。

网关重置
--------------------------------------------------------------------
1. 顶部按钮明确命名为“重置网关”，不是“刷新页面”。
2. 显示确认：将停止旧监听器并随机选择新端口，线路、模型、客户端 Key、统计
   和同步数据保留；Cherry Studio 需要重新复制本地 API 地址。
3. 停止旧 HTTP server，确认旧端口不再监听。
4. 在 20000-48999 的 29,000 个候选端口中安全随机探测可用端口。
5. 重新启动监听器和健康检查。
6. 更新顶部状态、API 地址、客户端 Key 页面和复制按钮。
7. 旧地址请求必须失败，新地址请求必须成功。
8. 重置只影响本地端口和进程缓存，不能改变 datasetId、routeId、clientId、
   永久总账、云端 vault 或同步设置。
9. 云端“重置/删除备份”必须是另一个危险操作，不能复用本按钮。

```text
中转线路
模型目录
客户端 Key

设置
```

不增加“本地路由”独立菜单。网关状态、端口、在线状态放总览和顶部状态胶囊。

统一二次确认窗口
--------------------------------------------------------------------
- 不再使用系统原生白色 MessageBox 与深色界面混搭。
- 使用统一的深色紫色 Modal：图标、标题、说明、影响范围、主按钮、取消按钮。
- 主按钮按风险使用紫色/红色；删除使用错误色 #F16C8C。
- 文字必须明确“会改变什么”和“不会改变什么”。
- 关闭网关重置、删除客户端 Key、删除线路、删除云端备份、清空明细使用不同文案。
- 键盘 Esc 取消；Enter 不直接触发永久删除，危险操作需要明确点击。

设置页
--------------------------------------------------------------------
设置分为四组，避免两个含义重复的设置：

1. 应用行为
   开机自启、启动隐藏、关闭窗口进托盘、语言。
2. 网关
   当前地址、当前端口、复制地址、重置网关、网关状态。
3. 云同步
   Active Provider、GitHub 账户、datasetId 摘要、同步开关、立即同步、
   30 分钟周期、待同步数量、上次同步、下次同步、恢复、删除云端备份。
4. 安全与更新
   加密密码/恢复码、密钥轮换、检查更新、数据目录和脱敏日志入口。

使用统计页
--------------------------------------------------------------------
- 顶部卡片：永久累计 Token，明确标注“没有时间限制”。
- 第二组卡片：当前筛选范围的总 Token、输入、输出、缓存命中率、请求数。
- 折线图：输入、输出、缓存读取、缓存创建、成本；悬停显示 UTC+8 精确时间。
- 过滤器：24 小时、7 天、30 天、90 天、半年；线路、模型、成功/失败。
- 请求表：时间、线路、模型、思考强度、输入、输出、缓存、总 Token、耗时、状态。
- 明细清理提示必须说明“只清理可查询明细，不减少永久累计”。
- 中英文切换时标题、图例、表头、空状态、单位、错误和保留说明一起切换。

中英文规则
--------------------------------------------------------------------
- 所有用户可见文本使用 i18n key。
- 不把“medium”误翻成不一致的多种写法；五档值保留统一英文枚举。
- 英文较长时按钮允许自适应宽度，不截断成半句话。
- 中文和英文都要测试窄窗口、长线路名、长模型名和错误信息换行。

====================================================================
十六、0.4.4 到 1.00 的迁移方案
====================================================================

迁移原则
--------------------------------------------------------------------
1. 迁移前停止旧网关写入并创建带时间戳的本机备份。
2. 不删除原始 JSON，不覆盖旧版本目录。
3. 读取并校验旧配置后生成 schemaVersion=1 的 config.json。
4. 将旧 usage.json 中的每条可用记录转换为 usage_events；无法解析的记录保留
   在迁移报告中，不伪造 Token。
5. 从旧永久总账创建初始 counter；迁移导入事件必须有明确的 migration deviceEpoch。
6. 旧客户端 Key 如果只有摘要没有密文，标记不可恢复，不能假装能复制。
7. 旧 API URL、上游 Key、认证信息迁移到 vault；如果旧数据无法安全解密，
   保留原文件并要求用户重新输入，不把空值上传云端。
8. 迁移失败时关闭新版本写入，恢复旧目录并显示原因。
9. 迁移完成后写 migration-state=committed，后续启动不重复导入。
10. 用户未连接 GitHub 时，迁移数据永不自动上传。

未来版本兼容
--------------------------------------------------------------------
- manifest 的 schemaVersion、minReaderVersion、minWriterVersion 必须存在。
- 1.01 可添加字段但不能破坏 1.00 的读取；新字段使用默认值。
- 1.10 如果修改核心结构，必须提供迁移器和回滚点。
- 老客户端遇到新 schema 不能写入，宁愿只读或提示升级，也不能破坏云端数据。

====================================================================
十七、更新检查、安装包和托盘
====================================================================

更新检查
--------------------------------------------------------------------
1. 只读取指定 GitHub 项目的公开 Release API 或 latest Release 页面。
2. 不带本地配置、usage、Key、Token 或设备信息。
3. 只显示当前版本、最新版本、发布日期、更新说明和下载页面入口。
4. 不自动下载、不自动替换、不自动安装正式版。
5. API 限流时使用可读错误或官方页面入口，不无限刷新。

安装包
--------------------------------------------------------------------
- 目标为 Windows x64 NSIS。
- EXE 自带 Electron、Node.js 运行时和 SQLite 原生模块。
- 用户不需要提前安装 Node.js、npm、pnpm 或独立 SQLite。
- per-user 安装为默认，不无理由申请管理员权限。
- 安装时可以选择目录，默认行为稳定。
- 运行时数据放在软件 EXE 所在目录的 data 子目录，安装到 D 盘时数据也跟随到 D 盘。
- 用户删除软件目录或卸载前，界面和文档必须提醒：data 同时包含缓存、线路、客户端 Key、
  永久统计和未同步数据；需要保留时先同步或备份整个 data。
- 重装保留数据和全删数据分别测试，不能默认承诺卸载器会保留安装目录内的 data。
- 没有代码签名时，README 必须说明 Windows SmartScreen“未知发布者”提示；
  后续正式公开发布建议使用代码签名证书。

托盘
--------------------------------------------------------------------
- 启动隐藏开启时，应用启动后只显示托盘，不弹主窗口。
- 关闭窗口默认最小化到托盘，网关继续运行。
- 托盘菜单至少包含显示窗口、暂停/恢复自动同步、复制本地 API 地址、退出。
- 托盘图标必须在 Windows 任务栏隐藏图标区域真实可见。
- 测试不能只看开发环境窗口，必须看打包后安装程序。

十八、严格开发顺序和每阶段出口
====================================================================

Phase 0：冻结和扫描
--------------------------------------------------------------------
- 保存 0.4.4 源码、安装包、数据目录和证据。
- 扫描仓库、dist、日志、测试数据和文档中的真实密钥。
- 盘点当前 JSON/usage/IPC/gateway 字段，写出迁移表。
- 出口：形成当前结构清单，零真实密钥，旧版本可回退。

Phase 1：风险登记
--------------------------------------------------------------------
- 建立 P0/P1/P2/P3 风险表，列出负责人、修复版本、测试证据和关闭条件。
- 出口：每个 P0 有明确测试，不允许“以后再看看”。

Phase 2：先写同步协议
--------------------------------------------------------------------
- 新建并维护 sync/SYNC-PROTOCOL.md。
- 先确定 manifest、generation、datasetId、文件命名、上传顺序、GC 和恢复流程。
- 出口：协议字段固定，代码不得自行发明另一套格式。

Phase 3：本地可靠存储
--------------------------------------------------------------------
- 引入 SQLite usage.db、WAL、事务、outbox、tombstone、deviceEpoch 和 eventId。
- 保留 config.json，建立 atomic temp + rename 写入。
- 出口：断电/强制结束测试后，本地请求记录和队列不丢。

Phase 4：合并与代数提交
--------------------------------------------------------------------
- 实现 immutable asset、manifest last、远端再读、G-Counter、冲突和 mark-and-sweep。
- 出口：两台/三台设备并发不重复、不静默覆盖、不因旧设备回写而丢失。

Phase 5：vault 和安全
--------------------------------------------------------------------
- 实现压缩、Argon2id、DEK/KEK、AES-256-GCM、恢复码、keyEpoch、vaultRevision。
- 出口：错误密码、篡改 ciphertext、错误 datasetId 都不会修改当前本机数据。

Phase 6：GitHub Provider
--------------------------------------------------------------------
- 实现授权、私有仓库、固定 Release、资产上传下载删除、限流和撤销授权。
- 出口：Fake Provider 全错误矩阵通过，真实 GitHub 小规模验收通过。

Phase 7：可选云盘
--------------------------------------------------------------------
- 实现 Google Drive appDataFolder 和 OneDrive approot 的接口适配。
- 出口：失败不影响 GitHub 和本地网关；权限和账户变更可恢复。

Phase 8：同步状态和界面
--------------------------------------------------------------------
- UI 显示状态机、待同步数量、上次/下次同步、冲突和恢复预览。
- 出口：用户能看懂“未连接、已同步、等待重试、需要登录、冲突、数据损坏”。

Phase 9：核心产品功能
--------------------------------------------------------------------
- 线路、模型目录、客户端 Key、复制、编辑、停用、删除、五档思考强度、网关重置。
- 出口：不破坏 0.4.4 已确认的本地功能。

Phase 10：统计和剪枝
--------------------------------------------------------------------
- 永久 G-Counter、实时明细、趋势、缓存命中率、半年查询范围、50/45 MiB 容量剪枝和 compaction。
- 出口：剪枝后永久累计完全不变，多设备合并不重复。

Phase 11：桌面和安装
--------------------------------------------------------------------
- 托盘、图标统一、开机自启、启动隐藏、进托盘、双语、更新检查、NSIS。
- 出口：开发环境和安装后环境分别通过验收。

Phase 12：自动化测试和故障注入
--------------------------------------------------------------------
- FakeCloudProvider、每步中断、竞态、属性测试、恢复和安全测试。
- 出口：P0/P1 全通过，失败用例有修复记录。

Phase 13：人工验收和文档
--------------------------------------------------------------------
- 先开发自测，再测试人员验收，最后用户验收。
- “待验收”和“待用户验收”严格分开，不能互相冒充完成。
- 出口：测试人员文档和结果报告完整。

Phase 14：正式发布
--------------------------------------------------------------------
- 版本号 1.00，构建、签名/未签名说明、SHA-256、README-CN/EN、CHANGELOG、
  安全说明、同步故障排查和安装包清单齐全。
- 出口：只有最终报告写出 READY FOR 1.00 INSTALLER 才可发包。

====================================================================
十九、自动化测试和人工验收矩阵
====================================================================

A. 本地网关基础
--------------------------------------------------------------------
1. 启动、单实例、托盘、隐藏、关闭进托盘和退出。
2. 127.0.0.1 监听；默认不监听 0.0.0.0。
3. 端口冲突和随机端口；旧端口失效、新端口健康。
4. 线路增删改、绑定数量、检测未检测/成功/失败状态。
5. /v1/models 只返回绑定线路模型。
6. Responses/Chat Completions，流式/非流式，错误和超时。
7. low、medium、high、xhigh、max 五档前后端和上游字段一致。
8. 客户端 Key 创建、默认名称、名称跟随、自定义锁定、复制、编辑、停用、
   启用、永久删除和删除后认证失败。

B. 统计和数据库
--------------------------------------------------------------------
1. 请求结束先写 usage_events、counter、outbox，再返回可接受结果；模拟写入失败。
2. 重复 eventId 不重复计数。
3. 断号检测、设备克隆、deviceEpoch 递增。
4. 24 小时、7 天、30 天、90 天、半年筛选。
5. 永久累计不受时间筛选、重启、重置、语言切换和剪枝影响。
6. 上游无 usage 时 Token=0，仍有状态和耗时。
7. 多设备同 event、不同 event、同模型和不同模型统计准确。
8. WAL 崩溃恢复、SQLite 备份可读、迁移前后计数一致。

C. GitHub Fake Provider 错误注入
--------------------------------------------------------------------
必须能够注入并验证：
401、403、404、409、412、422、429、500、502、503、504、超时、断网、连接重置、
部分上传、上传后崩溃、manifest 上传中断、校验失败、仓库 public、Release 被删、
Asset 被删、授权撤销、Retry-After、速率头缺失和响应体损坏。

D. 每个同步步骤故障注入
--------------------------------------------------------------------
1. 生成本地 payload 前失败。
2. 上传第一个数据资产时失败。
3. 上传部分 usage 分片后失败。
4. 数据资产全成功但 manifest 未上传。
5. manifest 上传一半或响应丢失。
6. manifest 成功但本地未收到确认。
7. manifest 成功后 GC 中断。
8. GC 删除一部分后崩溃。
每一步重新启动后都不能丢本地数据，不能把未 committed 资产当成有效数据。

E. 多设备和属性测试
--------------------------------------------------------------------
1. 设备 A 100 条、设备 B 50 条，合并后 150 条。
2. 同一事件被重复上传，结果仍只计一次。
3. 不同字段修改自动合并。
4. 同一字段修改产生冲突预览。
5. 删除 vs 修改产生冲突，不静默复活或静默覆盖。
6. 同步顺序改变，最终事件集合相同。
7. merge(A,B)=merge(B,A)。
8. merge(A,A)=A。
9. merge(merge(A,B),C)=merge(A,merge(B,C))，在适用的无冲突事件集合上成立。
10. 复制数据目录到第二台机器，不能保持相同 deviceId + sequence 写入。

F. 加密和恢复
--------------------------------------------------------------------
1. 正确密码可解密，错误密码不可解密。
2. 恢复码可恢复，恢复后建议轮换。
3. 篡改 ciphertext、tag、nonce、AAD 或 datasetId 必须失败。
4. 错误密码不清空本地 vault，不创建空配置。
5. 密码变更只改变包裹信息时 keyEpoch 不变，vaultRevision 变化。
6. DEK 轮换时 keyEpoch 递增，旧设备不能覆盖新 vault。
7. 日志、manifest、summary、config、usage 和 crash 不含完整秘密。
8. Base URL 恢复前要求确认；禁止静默把真实 Key 发往未验证地址。

G. 容量和压缩
--------------------------------------------------------------------
1. usage JSONL 可解压、逐行 schema 正确、损坏时拒绝。
2. gzip bomb 和超大解压结果被限制。
3. 16 至 20 MiB 目标分片和 24 MiB 硬限制生效。
4. 800 资产提醒、900 资产安全清理。
5. 当前代和三个回滚代仍完整可恢复。
6. 清理明细后永久总账不变。

H. 安装和升级
--------------------------------------------------------------------
1. 全新安装不需要用户预装 Node.js 或 SQLite。
2. Windows 10/11 x64 安装、启动、托盘和网关正常。
3. 0.4.4 到 1.00 迁移前备份可读，失败可回滚。
4. 保留数据重装后线路、Key、统计和同步状态仍可用。
5. 用户选择删除数据时才清除 user data；卸载程序文件不能误删用户数据。
6. 升级到未来 schema 时旧客户端只读或提示升级，不能覆盖新数据。

I. P0 发布阻断项
--------------------------------------------------------------------
- 任意完整 API Key、客户端 Key、Token 或聊天正文上传云端。
- usage 丢失、重复计数、永久总账减少。
- 配置静默覆盖或删除后复活。
- 错误密码覆盖正确 vault。
- 旧客户端覆盖新 schema/keyEpoch。

====================================================================
二十二、和原来方案相比，最终版改了什么
====================================================================

1. 原来只说“配置 JSON + usage 文件”，现在确定为“config.json 保持简单，
   usage.db 承担事务、总账、队列和墓碑”，解决断电、重复和并发问题。
2. 原来倾向每次只保留一个最新 Release 附件，现在改为“不可变 generation +
   manifest 最后提交 + 当前代/三代回滚 + mark-and-sweep”，既减少历史，又不
   因上传中断而丢掉上一份完整数据。
3. 原来 summary 可以直接相加，现在改为 deviceId + deviceEpoch 的 G-Counter，
   解决多设备同步重复累计。
4. 原来删除对象的同步规则不够明确，现在增加 tombstone，解决离线设备复活删除。
5. 原来只强调上游 API Key 加密，现在把 Base URL、代理、TLS、认证方式等安全
   连接配置全部放进 vault，降低误发真实 Key 的风险。
6. 原来可以用“密码派生密钥后直接加密”描述，现在固定采用 DEK/KEK 信封加密、
   Argon2id、AES-256-GCM、恢复码、keyEpoch 和 vaultRevision。
7. 原来恢复偏向直接替换，现在固定为下载校验、解密、限界解压、预览、合并、
   原子提交，保护本地未同步数据。
8. 原来可把 GitHub、Google Drive、OneDrive 都理解成同时同步，现在确定一主多
   可选镜像，避免三套云端互相覆盖。
9. 旧稿中的“云端 5GB/8GB”不再作为 1.00 本机缓存规则；当前本机明细按
   50/45 MiB 清理。GitHub 云端只保留资产数量、单资产大小、校验和安全垃圾回收限制。
10. 原来重点在功能列表，现在增加 Fake Provider、故障注入、多设备竞态、属性
    测试、安装重装和云端损坏测试，1.00 以恢复能力而不只是界面作为验收重点。
