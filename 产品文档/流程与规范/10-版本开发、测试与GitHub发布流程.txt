# 【最高优先级】版本开发、测试与 GitHub 发布流程

这是唯一的高权重防错文档；与其他文档冲突时以本文件为准，每次检查发现流程问题，必须先在本文件追加一条短规则，再开始下一次同类检查。

## 版本开始

- 先阅读文档索引、当前版本记录、测试清单和待处理问题。
- 新建版本记录，写明目标、范围、不处理项、验收标准和证据位置。
- 保留旧版本源码、安装包、哈希、Release 和截图，不覆盖历史文件。
- 用户明确说“开始修复”后才能改代码，用户只说“记录”时只能改文档。
- 当前版本发现的新问题默认登记到下个版本，不得顺手修复。

## 开发检查

- 修改前先复现并确认根因，避免只修复表面现象。
- 代码按模块、功能和职责拆分，模块内部按配置、数据、状态、请求和界面分区。
- 注释说明目的、关键规则、安全边界和异常处理，让其他维护者能够读懂。
- 只修改当前版本范围内的文件，不混入无关重构、视觉调整或依赖升级。
- 涉及数据、客户端 Key、同步和更新时，必须保持原有安全规则不变。

## 测试检查

- 先运行 `npm run check`，失败时记录原因，不删除检查项。
- 再运行 `npm test`，失败测试必须判断是本次改动、环境问题还是历史问题。
- 再运行 `npm run renderer:build`，确认前端能够完成生产构建。
- 浏览器测试必须覆盖默认窗口、缩放、最大化、语言切换、刷新、重启和异常网络。
- 更新测试必须覆盖版本读取、安装包地址、哈希缺失、哈希错误、下载中断和更新后数据保留。
- 更新检查遇到 GitHub API 限流时，必须确认仍能读取官方 Release 资产和 SHA-256。
- 同步测试必须覆盖首次同步、再次同步、断网恢复、冲突、旧数据和新设备恢复。
- 同步出现超时时，必须记录错误码、下一次重试时间和最终恢复结果。
- 每个失败项记录版本、环境、步骤、预期、实际、复现概率和证据位置。
- 没有实际操作或证据的项目只能写“待确认”，不能写“已通过”。

## 构建检查

- 用户明确批准制作安装包后才能运行 `npm run dist`。
- 构建后核对版本号、文件名、平台、文件大小和 SHA-256。
- 安装包不得包含密钥、令牌、真实测试数据、临时文件或重复资产。
- 构建期间发现无关问题时只登记到下个版本，不为了通过检查而绕过测试。

## GitHub 发布检查

- 只有用户明确要求上传或发布时才能操作 GitHub。
- 上传前确认工作树、版本号、tag、README、Release 说明、安装包和哈希一致。
- 每个版本只上传唯一正确的安装包，不上传旧包、临时包或敏感截图。
- 发布后核对主页、Latest、tag、Release 正文、下载链接、文件大小和 SHA-256。
- 发布后分别验证 API 正常、API 限流、安装包缺哈希和哈希错误时的安全行为。
- 发布后复核启动、更新、数据目录、客户端 Key、同步、重启和托盘行为。
- 将发布结果、未完成验收项、风险和证据写回版本记录。

## 流程问题记录

格式：`日期｜版本｜检查环节｜发现的问题｜新增防错规则`

规则：一条问题只写一句话；已写入本文件的规则，后续检查必须执行并留下证据。
