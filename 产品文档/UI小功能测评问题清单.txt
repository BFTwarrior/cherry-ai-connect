Cherry 多线路网关桌面版
UI 与小功能持续测评问题清单

文档状态：持续维护
首次建立：2026-09-10
当前测试版本：1.00 候选版（下方 0.4.1-0.4.4 条目为历史记录）
测试平台：Windows x64

一、使用规则

1. 本文件专门记录用户角度的 UI、交互、小功能和信息架构问题，不把“能运行”当成“体验合格”。
2. 《测试人员完整说明.txt》只作为测试范围和预期行为参考，其中的自检记录不自动视为本次实测证据。
3. 问题状态使用：待修复、待验收、待用户验收、已验收待删除。`待验收`表示开发修复和开发侧回归已完成，等待测试人员按步骤执行验收；`待用户验收`表示需要用户本人确认最终视觉、托盘、Cherry Studio 对话或使用体验。
4. 修复后必须重新验证。开发侧完成代码、构建或接口回归后可标记为“待验收”；涉及用户本人体验的项目继续标记为“待用户验收”；用户明确验收后才改为“已验收待删除”。
5. 只有用户明确验收后，才从本文件删除对应问题；删除前保留完整复现和验收记录。
6. 本文件不记录任何真实上游 API Key、客户端完整 Key 或其他敏感凭证。

严重程度：
- P1：会误导用户、阻断关键流程或导致凭证/配置风险，应优先处理。
- P2：明显影响日常使用、配置可信度或平台适配，应在正式发布前处理。
- P3：视觉、信息架构或细节体验问题，可以排在功能性问题之后，但不能假装不存在。

二、当前问题清单

UI-001 [P2] 右上角“思考 HIGH”看起来像控制项，实际不能直接调整
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：总览及所有页面右上角

实际表现：
- 右上角显示“思考 HIGH”，用户自然会理解为当前可操作的思考强度控制。
- 点击后只跳转到设置页，不能直接切换 LOW、MEDIUM、HIGH、XHIGH、MAX。
- 它与总览中的“默认思考强度”重复显示，作为按钮却没有快捷调整功能，交互意义很弱。

问题判断：
这是一个“看起来能改、实际只能导航”的假控制。要么改成纯状态标签并去掉按钮样式，要么提供真正的下拉/快捷选择，并明确提示这是默认值还是当前客户端 Key 的值。

建议验收：
- 点击右上角后应能直接选择等级并立即看到结果；或者改为非按钮状态展示，并在旁边提供明确的“前往设置”入口。
- 需要说明该值是否影响已有 Key，避免“默认值”和“Key 独立值”混淆。

UI-002 [P1] 设置中的默认思考强度不会同步到总览显示
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：设置页“默认思考强度”、总览页指标、右上角思考标签

复现步骤：
1. 当前默认值为 HIGH。
2. 将默认思考强度改为 LOW 并保存；管理接口返回保存成功，服务端值已经是 LOW。
3. 返回总览并观察右上角和“默认思考强度”指标。

实际结果：
- 服务端值改为 LOW 后，在不触发界面重新加载时，总览右上角仍显示 HIGH。
- 总览指标也会继续显示 HIGH，用户无法立即确认刚刚保存的 LOW 是否真正生效。
- 本轮手动点击顶部刷新并等待网关重启完成后，界面才同步显示 LOW。

问题判断：
这是配置状态和界面状态存在刷新时序差异，不能只归类为视觉问题。界面写着“真实写入转发请求”，却不能在配置变化后立即显示当前配置，容易造成误配置和错误验收。设置页保存后的完整交互链路仍需专项验收，不能要求用户额外点击顶部重启按钮才能看到新值。

建议验收：
- 分别在设置页保存 LOW、MEDIUM、MAX，保存完成后设置页、右上角、总览指标必须立即一致。
- 保存后切换页面、重新打开程序后仍必须一致。
- 如果已有客户端 Key 使用独立等级，必须同时显示“默认值”和“当前 Key 值”的区别。

UI-003 [P1] 客户端 Key 只显示一次，但复制结果没有可靠反馈
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：生成客户端 Key 后的唯一显示窗口

实际表现：
- 完整客户端 Key 只展示一次，这个设计本身合理。
- 点击“复制”后没有稳定、明确的成功或失败反馈。
- 本次实测无法确认剪贴板是否真的拿到了新生成的 Key；如果用户直接关闭窗口，凭证可能永久丢失。
- 复制异常时没有明显的备用操作提示。

问题判断：
这是关键凭证流程，不能让用户靠猜。窗口写着“这是唯一一次完整显示”，却没有可靠确认，是严重的交互闭环缺失。

建议验收：
- 复制成功必须显示成功 Toast；失败必须显示失败原因和手动选择复制方案。
- “我已保存，完成”前明确提醒用户确认已经复制或保存。
- 复制失败不能被静默吞掉。

UI-004 [P1] 线路异常只显示“异常”，不显示可处理的错误原因
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：线路页、总览线路概览

复现结果：
- 使用不可连接地址进行同步，后端实际得到 `ECONNREFUSED`。
- 页面只显示红色“异常”和 0 个模型，没有显示连接失败、地址错误、Key 错误等原因。
- 后端已经记录 `lastError`，但线路卡片没有呈现它。

问题判断：
这会把排障责任推给用户。一个网关工具最基本的失败反馈就是告诉用户“哪里错了”，仅给一个红色状态点属于敷衍完成。

相关代码位置：
- `gateway/gateway.mjs` 约第 337 行开始保存线路错误。
- `renderer/src/App.tsx` 约第 387 行开始渲染线路卡片，但没有渲染 `lastError`。

建议验收：
- 线路卡片或展开详情显示错误摘要。
- 同时保留简短用户提示和可复制的详细错误信息。
- 修复地址、Key 后，错误状态必须清除并显示新的检测结果。

UI-005 [P2] 总览“4/4 完成”并不代表真的在 Cherry 中成功使用
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：总览页 QUICK START

实际表现：
- 只要存在启用的客户端 Key，第四步就显示完成。
- 没有实际发出一次 Cherry 客户端请求时，也可以显示“在 Cherry 中使用客户端 Key”。
- 本次代码核对发现判断条件只是启用 Key 数量大于 0。

问题判断：
这是完成度定义错误。配置存在不等于配置验证成功，页面不应该用“4/4 完成”制造虚假的确定感。

建议验收：
- 第四步至少在本地成功完成一次真实请求后才完成。
- 未验证时显示“待验证”或“尚未检测”，并提供测试入口。
- 失败请求不能被计入完成。

UI-006 [P2] Windows 版本显示 Mac 快捷键，且目前没有对应快捷键处理
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：左侧导航“总览、线路、模型、客户端 Key”

实际表现：
- Windows 桌面程序显示 `⌘1`、`⌘2`、`⌘3`、`⌘4`。
- 源码中这些只是传给导航组件的展示文本；没有发现对应的 keydown 或快捷键注册处理。

问题判断：
这是平台适配和提示可信度问题。Windows 用户看到 Mac 的 Command 符号，会误以为存在可用快捷键；如果快捷键根本没有实现，就是虚假功能提示。

建议验收：
- Windows 显示 `Ctrl+1` 等真实可用快捷键，并完成实际响应；或者删除快捷键提示。
- macOS 和 Windows 的提示应根据平台自动变化。

UI-007 [P2] 顶部刷新按钮会重启网关，但没有明确的重启过渡态
状态：待用户验收（0.4.3 连续重置复测未复现，等待用户验收）
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：右上角随机端口/刷新按钮

实际表现：
- 点击后旧端口会停止，新端口需要一小段时间才开始监听。
- 这段时间内客户端请求可能失败，界面却可能已经显示了新的端口。
- 没有清晰的“网关重启中，请稍候”状态，也没有健康检查完成前的明确禁用说明。

问题判断：
功能最终能成功，但过程对正在使用的客户端不透明，容易造成用户误判为线路故障。

建议验收：
- 重启期间显示明确状态并禁用相关操作。
- 新端口健康检查成功后再显示“网关在线”。
- Toast 中说明端口已变化，以及客户端需要使用新的地址。

UI-008 [P3] “打开数据目录”存在重复入口，信息架构不够干净
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：左侧系统菜单、设置页安全与连接区域

实际表现：
- 两个入口执行同一个打开数据目录功能。
- 功能本身可用，但在这个规模的桌面工具里属于重复摆放，占用了本来就有限的设置页视觉空间。

问题判断：

- 保留一个主入口；另一个改为说明链接或删除。
- 如果确实要保留两个入口，应说明它们服务的场景不同，而不是两个完全相同的按钮。

UI-010 [P3] 总览入口过多，同一个动作被重复摆放
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：总览 Hero、统计卡、QUICK START、线路快照和左侧导航

实际表现：
- “中转站线路”同时可以从左侧导航、Hero 添加按钮、统计卡、快速开始第一步和线路快照进入。
- “客户端 Key”同时可以从左侧导航、Hero 管理按钮、统计卡和快速开始第三/四步进入。
- “同步模型”又同时出现在快速开始、模型目录、线路卡片和模型分组内。

问题判断：
这不是功能越多越好，而是一个小型桌面工具把同一条路画了四五遍。用户需要先判断“哪个入口才是主入口”，总览反而变成导航菜单拼盘。最大限度减少操作不等于复制按钮，而是让界面在当前状态下只给一个最合理的下一步。

建议：
- 保留左侧导航作为稳定入口，统计卡改为只读信息。
- 总览只保留一个根据当前状态变化的“下一步”主按钮；快速开始保留进度，但不要每一行都承担重复导航。
- 线路和模型同步统一到一个明确的同步入口，其他位置只显示结果摘要。

UI-012 [P2] 总览显示“默认中转站”，但用户没有地方设置它
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：总览 CURRENT ROUTING

实际表现：
- 总览显示“默认中转站 CDKS测试线路”，看起来像当前所有请求都会走这条线路。
- 设置页没有默认线路选择，创建客户端 Key 时又必须绑定具体线路。
- 当前网关实际优先使用客户端 Key 的绑定线路；这个“默认线路”主要是兼容回退信息，既不直观也不可操作。

问题判断：
这块信息会误导用户排查线路。用户看到请求异常时会盯着“默认中转站”，但真正决定路由的是 Key 绑定关系。一个不能修改、又不是当前主要路由规则的状态卡，属于多余且危险的产品暗示。

建议：
- 如果每个 Key 必须绑定线路，就把这块改成“当前 Key 绑定关系”摘要，或直接删除。
- 如果确实需要无绑定请求的回退线路，必须提供明确的设置入口并说明适用范围。

UI-013 [P2] 同一个设置在不同位置有不同的保存规则
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：右上角默认思考、设置页、语言和桌面行为

实际表现：
- 右上角默认思考下拉框选择后立即写入服务端。
- 设置页默认思考需要点击“保存设置”；开机自启、启动隐藏、关闭到托盘也依赖保存按钮。
- 语言切换又是点击后立即生效。

问题判断：
同一类“设置”同时存在立即保存和延迟保存，用户很容易把设置页改完后直接切走，事后才发现没有保存。右上角和设置页还提供了同一项默认思考控制，行为却不一致，属于不必要的认知成本。

建议：
- 统一成全部即时保存，或全部采用草稿加保存；不能混用。
- 如果保留保存按钮，页面离开前必须提示未保存，并在控件旁显示脏状态。

UI-014 [P2] 当前本地 API 地址不能在使用现场直接复制，也没有一键连通性测试
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：顶部地址胶囊、客户端 Key 页、设置页

实际表现：
- 顶部地址胶囊只展示地址，不能点击复制。
- 重置端口后，用户必须进入设置页，复制新 `/v1` 地址，再切换到 Cherry Studio 粘贴。
- 客户端 Key 卡片没有“测试此 Key”按钮，QUICK START 第四步也只能跳到 Key 列表，不能完成实际验证。

问题判断：
网关最常见的日常操作就是“复制本地地址、验证 Key 是否可用”。现在这条链路需要跨页面、跨软件手动完成，正好把最应该省掉的操作留给用户。

- Key 卡片提供“测试本地接口”按钮，使用该 Key 调用 `/v1/models` 并记录结果。

UI-015 [P3] “同步全部”没有进度和失败重试路径
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00
发现日期：2026-09-10
位置：模型目录“同步全部”

实际表现：
- 多条线路同步时只有一个“同步中”状态，用户看不到正在处理哪一条。
- 结束后只显示类似 `1/2` 的汇总；失败原因要回到线路卡片才看得到。
- 没有“仅重试失败线路”按钮，只能重新同步全部或逐条寻找。

问题判断：
线路一多，这个操作就会变成黑箱等待。批量功能如果不给进度、失败对象和重试入口，实际上没有减少维护成本。

建议：
- 显示“正在同步 2/5：线路名”和每条线路的实时结果。
- 汇总区直接提供“重试失败项”。
- 失败线路不应让用户重新等待已经成功的线路。

UI-016 [P2] “重置并随机端口”外观像普通刷新，实际会改变客户端连接地址
状态：待用户验收
本轮时间戳：2026-09-10 18:34:21 +08:00

位置：右上角刷新图标

- 顶部使用常见刷新图标，用户很容易理解成“刷新页面或重新读取数据”。
- 实际操作会停止旧监听器、改变本地端口，让 Cherry Studio 原有 API 地址立即失效。
- 影响只在悬停提示和设置页说明中体现，首次使用者不一定会看到。

问题判断：
这是一个带破坏性影响的操作，却穿着普通刷新按钮的外衣。用户误点后会直接得到“Cherry 突然连不上”的故障，风险远大于普通 UI 刷新。

建议：
- 改成明确的“重启网关并换端口”文案或带文字按钮。
- 与“重新读取数据”彻底分成两个动作。
- 点击前提示旧地址会失效，完成后直接提供“复制新 API 地址”。

UI-017 [P2] 旧版 Key 仍显示可点击的“复制 Key”，必然失败后才告诉用户无法恢复
状态：待用户验收
本轮时间戳：2026-09-10 21:56:52 +08:00
发现日期：2026-09-10
位置：客户端 Key 卡片快捷操作

实际表现：

- 重新生成按钮应在同一行明确提示“会使旧 Key 失效”，并保留二次确认。

UI-018 [P1] 常见窗口尺寸下右侧关键操作被挤出视口

- 加入至少一个较小的普通窗口尺寸做人工验收，确认所有高频操作都能看见并点击，不要只在最大化截图下验收。

UI-019 [P2] QUICK START 完成项显示“查看”，实际仍会重新同步
状态：待用户验收
本轮时间戳：2026-09-10 22:49:48 +08:00
发现日期：2026-09-10
位置：总览页 QUICK START 的“同步上游模型目录”

实际表现：
- 当四步已经完成时，这一行的右侧文案显示为“查看”，用户自然会理解为进入模型目录查看现有结果。
- 本轮在 0.4.3 总览中点击该行后，实际跳转到模型目录并立即执行了批量同步；页面显示“已同步 2/2”，两条线路的模型更新时间也发生了变化。
- 也就是说，同一条完成项的可见动作写的是“查看”，真实动作却是重新访问上游并更新本地数据。用户只是想查看时，会被无提示地触发网络请求和等待。

问题判断：
这是按钮文案和行为不一致的确定性问题。同步是有副作用、有等待时间、可能失败的网络动作，不应该伪装成只读的“查看”。当前实现把“完成后的查看入口”和“再次执行同步”混成了一个动作，容易造成用户误解，也会让 QUICK START 的完成状态显得不可信。

建议：
- 完成后点击应只导航到模型目录，文案保留“查看”；需要重新拉取时由模型目录中的“同步全部”负责。
- 如果产品确实希望点击完成项就再次同步，文案必须改成“重新同步”，并在执行前后给出同步状态；不要继续显示“查看”。

本轮额外观察（暂不单列为已确认缺陷）：
- 顶部“默认思考”虽然有悬停说明，但常驻可见文案没有写清“只影响新建 Key”；建议直接显示“新建 Key 默认思考”，避免用户再次误以为它会改变现有 Key。
- 线路卡片的“可用”目前更接近“/v1/models 检测成功”。真正的客户端转发成功已经由 Key 的“测试连接”和总览最近一次转发状态单独表示，建议将线路状态文案改成“目录可用”或补充最近一次转发状态，避免把目录探测成功误解为完整对话链路已验证。
- 总览仍保留较大的装饰性欢迎区和路线摘要区；当线路、模型和 Key 已经配置完成后，用户最关心的是最近转发结果、失败原因和下一步动作，装饰内容的占比仍偏高。这属于信息密度和产品定位建议，暂不替代已有 UI-009、UI-010 条目。

本节结论：UI-017、UI-018、UI-019 已完成开发修复并经本轮现场复核，进入待用户验收；“新版 Key 从卡片复制完整 Key”和失败线路重试仍按本轮边界说明等待后续现场验收。

UI-020 [P2] “同步模型”入口过多，首次同步、单线路同步和全量同步没有收敛
状态：待用户验收
本轮时间戳：2026-09-10 22:54:43 +08:00
发现日期：2026-09-10
位置：总览、添加/编辑线路、线路页、模型目录

实际表现：
- 添加线路时，提交按钮本身就是“添加并同步”；编辑线路时是“保存并同步”。
- 线路页的说明要求用户点击“同步模型”，每条线路卡片又各自有一个“同步模型”。

问题判断：
这不是功能越多越好，而是同一个动作被包装成太多入口。首次配置、单线路刷新、全量刷新和查看结果没有形成清楚的层级，用户很容易重复同步，或者不知道“同步全部”和线路卡片“同步模型”有什么区别。总览、线路页、模型页都在承担模型同步职责，产品心智模型变复杂了。

- 把模型目录作为唯一的手动同步中心：模型页保留“同步全部”和单线路“同步”。
- 新增线路流程可以自动同步，但完成后只显示结果和“查看模型”；线路页卡片优先显示状态和“查看模型”，不要再放一个重复的同步入口，或明确写成“同步此线路”。
- 总览 QUICK START 只负责首次引导，已完成后进入模型目录查看，不再承担第二套同步入口。

UI-022 [P2] “把当前等级应用到已有 Key”是批量覆盖，却没有数量、影响范围和二次确认
状态：待用户验收
本轮时间戳：2026-09-10 22:54:43 +08:00
发现日期：2026-09-10
位置：设置 > 请求策略

实际表现：
- 设置页明确说明“已有 Key 保持自己的等级”，紧接着又放了一个宽大的“把当前等级应用到已有 Key”按钮。
- 当前按钮没有显示会影响几个 Key，也没有写明会覆盖已有 Key 的独立思考强度。
- 点击逻辑会直接提交 `applyToExisting: true` 并刷新数据，没有确认框、变更摘要或撤销入口。本轮没有点击它，避免改动现有正式 Key，但界面和代码已足以确认这是直接批量覆盖动作。

问题判断：
这是高影响配置，不应该和普通下拉选择放在同一层级、用普通次按钮表达。用户刚调整默认等级时，很容易把它误认为“保存”或“同步设置”，一旦点击就会抹掉每个 Key 原本的独立配置。这个功能不是完全没有价值，但默认设计明显不够谨慎。

- 更稳妥的做法是只应用到“跟随默认值”的 Key，已经单独设置过的 Key 默认不覆盖；或者把批量操作移到 Key 管理页。
