Cherry AI 连接中心 / Cherry AI Connect 踩坑记录

1. 旧版前端是静态 HTML/CSS/JavaScript，页面状态、弹窗、设置、线路和 Key 逻辑混在一起，导致功能能跑但界面冗余、后续改动容易互相影响。解决：升级为 React + TypeScript + Vite，并按总览、线路、模型、Key、设置拆分视图。

2. Vite 默认会生成以 / 开头的资源路径。Electron 使用 file:// 加载时会找不到 /assets 文件，表现为白屏或黑屏。解决：vite.config.mjs 设置 base: "./"，并让 Electron 加载 renderer/dist/index.html。

3. electron-builder 的 files 配置仍指向旧 renderer/**/* 时，打包包进的是源码入口而不是 Vite 产物。解决：改为 renderer/dist/**/*。

4. 【历史 0.4.x】旧版 EXE 仍占用本地网关端口，启动新版时会出现端口占用或新版没有真正接管请求。当前 1.00 已改为在 20000-48999 中安全随机选择可用端口；排障时仍不能误停其他软件。

5. 旧 config.json 中有历史客户端 Key 的 providerId 或思考强度为空。解决：启动时执行迁移，为旧 Key 补默认线路和默认思考强度，并补齐必要字段。

6. 旧线路有模型列表但没有检测状态。若直接显示“未检测”，用户会误以为模型同步没成功；若直接显示“可用”，又可能伪造检测结果。解决：有模型和同步时间的历史线路迁移为可用，没有历史记录的才显示未检测。

7. BrowserWindow 如果以隐藏状态启动，视觉测试工具会读到“窗口最小化/不可见”，看起来像应用没有打开。解决：普通启动显示窗口；只有设置了启动隐藏或传入 --hidden 时才隐藏到托盘。

8. PowerShell 可能因为执行策略阻止 npm.ps1，显示“无法加载文件，因为在此系统上禁止运行脚本”。Node 本身可能已经安装成功。解决：优先使用 npm.cmd，或由用户在可信环境中调整 PowerShell 执行策略；不要误判为 Node.js 未安装。

9. “同步模型成功”只说明 /v1/models 可访问，不等于聊天请求一定成功。聊天还受到模型权限、请求格式、代理/VPN、上游额度和思考参数兼容性的影响，必须分开测试。

10. 思考等级滑块只改本地 UI 文案没有意义。解决：网关根据客户端 Key 的设置，在 Responses 写 reasoning.effort，在 Chat Completions 写 reasoning_effort。

11. 线路 Key 和客户端 Key 拆开管理会让 Cherry 不知道该填哪个。解决：创建客户端 Key 时强制选择一条中转站线路；Cherry 只填写客户端 Key，线路 Key 留在网关本机。

12. 测试输出、截图和文档不能包含真实上游 API Key。所有验证只输出状态码、模型数量、线路代号或脱敏摘要。

13. 如果只修复托盘 PNG 而没有配置 build.win.icon，Windows 安装包和任务栏仍会显示默认 Electron 图标。解决：使用同一套产品图形生成 electron/assets/app.ico，在 build.win.icon 和 BrowserWindow.icon 中同时配置；托盘继续从同源 tray.png 加载。

14. 旧版桌面外目录被删除后，如果 main.js 还通过相对路径引用旧 gateway.mjs，打包和启动都会失败。解决：把 gateway.mjs 迁入当前项目的 gateway 文件夹，并让 electron-builder 把 gateway/**/* 一起打入 app.asar。

15. 仅关闭 Electron 窗口并不等于关闭 Node HTTP Server；重置时如果不先调用 server.close，下一次监听会遇到端口占用。解决：网关导出 stopGateway，主进程执行 stop -> 选择新的可用端口 -> start。

16. 刷新页面和重置网关是两个不同动作。当前产品把顶部刷新按钮定义为“刷新并重置网关”，它会随机切换可用本地端口，再重新加载界面数据；线路、模型、Key 和绑定关系保持不变。

17. Windows 托盘图标可能因为 SVG 数据不完整、图标尺寸过大或 AppUserModelId 缺失而不明显。解决：增加与 app.ico 同源的 electron/assets/tray.png 真实 PNG 资源，托盘优先从文件加载并缩放为 16 像素，同时设置应用标识，并让单击托盘图标恢复窗口。

18. 页面右侧滚动条在深色桌面 UI 中显得像多余的竖向导航。解决：隐藏 WebKit/Windows 滚动条，但保留滚轮、触控板和键盘滚动能力。

19. 右上角把默认思考等级做成只跳转设置页的按钮，会让用户误以为可以直接修改。解决：改为真正的五档下拉控件，并把默认值与客户端 Key 独立值分开说明。

20. 设置保存成功后如果只依赖下一次完整加载，界面可能继续显示旧等级。解决：使用受控状态接收服务端返回值，并在保存、快速修改和重新加载后同步设置页、总览和顶部控件。

21. 客户端 Key 只显示一次时，单纯调用 navigator.clipboard 可能在权限、焦点或桌面环境下失败。解决：增加失败捕获、Windows 备用复制路径、Toast 和手动选中复制提示。

22. 线路测试后端已经有 lastError，但只渲染“异常”会让用户无法排障。解决：将连接拒绝、域名错误、超时和 401/403 映射为可读摘要，并在卡片上提供复制详情。

23. “存在客户端 Key”不能证明 Cherry 真实转发成功。解决：网关记录最近一次客户端请求状态，只有真实上游响应成功才完成总览第四步。

24. 重置网关时过早清除重启状态会让新端口在数据尚未加载时看起来已经在线。解决：保持重启态直到管理接口和健康数据全部加载完成，再显示在线和新端口提示。

25. 最近一次客户端请求只保存在内存时，重启会让总览错误地回到“未测试”。解决：将请求时间、状态和模型写入配置；读取状态时只返回摘要，不返回客户端或上游密钥。

26. 仅调用 server.close 不能保证 Keep-Alive 连接立即结束，重置时可能一直等不到 close 回调。解决：跟踪活动 socket，停止时主动 destroy，并在关闭前调用 closeIdleConnections/closeAllConnections。

27. 总览把统计卡、欢迎区和页面入口都做成可点击，会让用户无法判断哪个是真正操作入口。解决：统计卡只读，欢迎区只保留动态下一步，QUICK START 每行对应一个实际动作。

28. 批量同步只显示最终结果时，失败线路和已成功线路混在一起，用户只能全部重试。解决：保存当前进度和失败 ID，提供只重试失败线路的入口。

29. 总览显示一个无法配置的“默认中转站”会和“一客户端 Key 绑定一条线路”的产品规则冲突。解决：改为显示有效客户端 Key 的实际绑定线路，未配置时显示明确空状态。

30. 设置页把即时保存和统一保存按钮混在一起，用户无法判断改动是否已经生效。解决：每个开关和语言选择即时保存；思考强度另设“应用到已有 Key”动作，避免误改已有 Key。

31. 本地 API 地址只显示文本、Key 只提供生成而没有测试入口，会把网络故障留到 Cherry 才暴露。解决：地址提供复制按钮，Key 卡片提供本地 `/v1/models` 测试，并持久化最近测试结果。

32. “刷新”这个词掩盖了重置会改变端口的事实。解决：改为“重置网关”，确认框明确旧地址失效、端口随机、线路/模型/Key 保留；前端在管理数据重新加载完成前保持重启态。

33. 桌面控制工具初始化失败时继续反复重试会浪费测试时间且不能产生有效视觉证据。本轮约定最多初始化两次；两次均失败后，只报告接口/构建结果，并把真实点击、托盘和 Toast 留给测试人员现场验收。

34. 旧版客户端 Key 只有摘要和哈希，没有可恢复的本地密文；如果列表页直接显示“复制 Key”会造成用户误解。解决：返回 hasSecret，旧版显示“重新生成”，确认后让旧 Key 失效并生成新的加密密文。

35. 为了方便用户复制而直接把客户端完整 Key 放进列表 DOM，会增加截图、辅助树和日志泄露风险。解决：卡片只显示脱敏摘要，点击复制时通过本机管理接口短暂取值；接口只服务本机，不返回上游 API Key。

36. 通过本机管理接口删除测试 Key 后，已经打开的前端页面不会自动知道数据变化，可能暂时仍显示旧卡片。解决：测试清理后刷新渲染器，再核对列表数量；正常用户删除流程由前端删除后自动重新加载。

37. 重置网关不能只验证“新端口出现”，还要验证旧地址失效和业务数据保留。解决：同时访问旧/新 health，读取线路、模型、Key 数量和最近成功状态；旧端口连接失败、新端口 ok=true 才算完整通过。

38. 多份文档各自追加状态时，历史“待验收”和“待用户验收”容易被误读为同一个状态。解决：增加 `00-交付总览与文档索引.txt` 作为统一入口，明确三种状态定义，并规定历史章节只用于追溯，最新交付摘要优先。

39. 文档写“数据目录”但没有区分源码目录、打包资源目录和 Electron userData，测试人员会在错误位置寻找配置。解决：统一要求通过“设置 > 打开数据目录”进入实际的 `gateway-data`，并明确 config.json 与 .gateway-secret 的敏感性。

40. 文档如果只写“构建通过”，却没有列出测试先后顺序，测试人员容易先改正式数据再排查网关。解决：固定为健康检查、线路/模型、临时 Key 生命周期、五档思考强度、Cherry Studio、语言/托盘、重置、清理临时数据。

41. 版本号和产品目标沿用旧版本会让测试人员误以为当前包不是 0.4.3。解决：产品目标、README、版本说明和交付索引统一标注 0.4.3；历史测试章节继续保留原版本号并说明其历史性质。

42. 文档补全本身不能替代用户验收，也不能把未执行的桌面视觉点击写成通过。解决：最终文档明确开发证据、测试人员验收和待用户验收的边界；不记录真实凭证，不改变用户数据。

43. Electron 窗口的标题栏和边框会减少网页实际可用高度，如果渲染层另设固定 `min-height`，低高度窗口会把侧栏底部信息推到视口外。解决：由 Electron 的 `minHeight` 负责窗口约束，渲染层使用 `min-height: 0`，并让侧栏状态卡和版本行保持不可压缩；同时用更紧凑的总览欢迎区释放首屏空间。

44. 如果只依赖半年明细重算“累计使用量”，明细剪枝后总量会莫名减少。解决：使用独立 lifetime 总账，每次请求先累加总账，再清理明细；查询时绝不用剩余明细覆盖总账。
45. 流式 SSE 的 usage 常在最后一个 data 事件，只解析普通 JSON 会丢失流式 Token。解决：保持边收边转发，同时仅解析 SSE data 行的 usage，不保存聊天正文。
46. 不同 OpenAI 兼容上游使用 prompt_tokens/completion_tokens 或 input_tokens/output_tokens，缓存字段也不一致。解决：做兼容字段归一化；上游不提供 usage 时保持 0，不根据文本长度估算。
47. 客户端 Key 名如果每次强制跟随线路名，会覆盖用户标签；完全不同步又增加创建负担。解决：增加 nameCustomized，自动阶段跟随，用户手动改名后永久保护该名。
48. 浏览器预览页没有 Electron IPC，“检查更新”只能验证排版，不能代表真实检查通过。解决：代码、视觉和打包版 GitHub 网络分开验收。

49. GitHub 匿名 Release API 会按公网出口限流，同一出口访问较多时会返回 403，这不代表项目没有 Release。解决：先尝试 API，失败后从 GitHub 官方 `releases/latest` 的 302 跳转地址解析 tag；两条通道都失败才向用户显示错误。
【1.00 当前实现覆盖（2026-09-16）】
以下规则覆盖本文后面旧版本记录中的同名参数：
1. 运行数据放在程序安装目录旁的 data；开发运行使用项目根目录 .runtime-data；不要再按旧文档猜测用户目录。
2. 使用明细缓存上限 50 MiB，超过后清理到约 45 MiB；“最近 200 条”只是界面分页，不是存储上限；永久累计总账不受清理影响。
3. 网关端口在 20000-48999 中使用系统安全随机数选择，重置时跳过当前端口和占用端口。
4. 当前安装包为 1.00 候选版，不得把开发侧通过写成最终用户验收通过。
