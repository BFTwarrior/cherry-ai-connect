# Cherry AI Connect 严重问题核查文档

更新时间：2026-09-23（UTC+8）

## 文档用途

本文件用于记录会造成数据丢失、同步失效、错误发布或安全边界破坏的严重问题。
后续每次版本开发、更新、同步、加密解密拆分、安装包构建和 GitHub 发布前，必须优先核查本文件；未完成核查或没有证据的项目只能标记为“待确认”。

## P0：本地数据不得丢失或被旧数据覆盖

- 更新、重启、卸载重装和异常恢复不得删除、清空或回滚 `data/`。
- `usage.db`、路由配置、客户端 Key、加密保险库和同步状态必须分别核对更新前后是否保留。
- 更新恢复指针必须绑定目标版本，并且只能一次性消费；已消费、旧版本或未来版本指针不得再次恢复。
- 发现空目录、部分目录、版本不匹配或恢复异常时，必须保护性停止，不能用空数据继续启动。
- 旧备份只能保留和待人工核对，不得静默覆盖当前数据。
- 验收必须包含：旧版本到当前版本覆盖更新、连续重启、更新失败后再次启动、数据目录权限异常和恢复中断。

## P0：同步必须可验证、可恢复、不可静默丢失

- 同步模块必须单独拆分，不能把同步失败隐藏在界面成功状态中。
- 必须分别核查 GitHub 凭据、匿名用量数据、加密保险库和同步 manifest；任何一项失败都要有明确状态和错误原因。
- 加密保险库故障不得阻塞用量同步，也不得覆盖或删除上一份有效的云端敏感配置。
- 同步失败必须记录错误类型、失败时间、下次重试时间和最终恢复结果。
- 必须覆盖首次同步、再次同步、断网恢复、GitHub 超时、fetch 失败、冲突、旧数据恢复和新设备恢复。
- 同步完成后必须核对本地数据、云端 manifest、版本号、数据序列号和恢复结果，不能只看按钮提示。
- 任何同步重试必须幂等，不得重复生成、覆盖或上传错误版本的数据。
- 未填写上游 API Key 不得阻塞本地模式、界面使用、配置保存或安全更新；只有实际调用上游线路时才报告线路 Key 缺失。

## P0：加密与解密边界

- 加密模块和解密模块必须独立于同步模块，明确输入、输出、版本、密钥来源和失败行为。
- GitHub 不得保存明文客户端 Key、密码、访问令牌或未加密保险库。
- 解密失败、密钥不匹配、数据损坏和版本不兼容时，必须保留原始有效数据并给出可定位错误。
- 任何加密格式变更必须提供版本标记、兼容策略和回滚验证，禁止无版本覆盖旧密文。
- 发布前检查安装包、Web Demo、日志、临时目录和上传资产，不得包含密钥、令牌或真实敏感数据。

## P0：版本与 GitHub 发布一致性

- `package.json`、锁文件、网关健康检查、渲染器显示、安装包文件名、`latest.yml`、tag 和 Release 正文必须使用同一版本。
- Release 只允许上传唯一正确的安装包、blockmap、Web Demo 和 `latest.yml`，不得混入旧包、临时包或敏感截图。
- 发布前必须核对工作树干净、测试结果、安装包大小、SHA-256、SHA-512 和平台架构。
- 发布后必须逐项核对 GitHub Release 的公开状态、Latest、tag、正文、下载链接、文件大小和远端哈希。
- 必须验证缺哈希、哈希错误、安装包下载失败和 GitHub 网络超时时的安全行为。
- 发布后必须复核启动、覆盖更新、数据目录、客户端 Key、同步、重启和托盘行为。

## 当前重点问题

### 使用统计旧明细被默认时段隐藏

本机只读核查确认 `usage.db` 完整性为 `ok`，保留 211 条请求（9 月 16 日至 22 日）；更新恢复备份保留 201 条，均属于同一数据集。默认 24 小时范围只有 10 条，因此旧请求被界面范围条件隐藏，而不是数据库丢失。

修复要求：图表时段只影响统计趋势和摘要；历史列表读取本机缓存中的全部时间范围，按 200 条分页并显示总数。源码已修复；本机安装后的全部分页确认待完成。

### 1.31 更新恢复回滚本地数据

状态：已修复并发布；后续版本必须回归验证。

根因是遗留的旧恢复指针在版本不匹配或多次启动时仍可能触发旧备份恢复，导致本地 `usage.db` 等数据回滚。1.31 已增加版本绑定、一次性消费和空/不完整数据保护；详见 `版本记录/15-1.31更新恢复回滚修复验收.txt`。

### GitHub 同步持续失败

状态：必须继续重点核查；`fetch failed`、`GitHub request timed out` 等错误必须区分网络问题、凭据问题、远端 API 问题和本地同步逻辑问题，不得以“稍后重试”代替定位。

### 无上游 API Key 用户的安全更新

状态：已纳入更新流程规则。安全更新只依赖 GitHub Release 的可访问性、安装包完整性和 SHA-256 校验，不应要求用户先填写上游 API Key。若更新失败，界面必须明确显示是 GitHub 网络问题、同步问题、安装包校验问题还是线路 Key 缺失；不得把这些原因混成一个“需要处理”。

### 1.31 已消费恢复指针导致启动崩溃

状态：1.32 已修复并发布；1.33 自动回归继续通过。`update_recovery_data_missing_after_consumption` 不得以 Electron 未捕获异常阻断主进程；修复恢复仍须验证备份版本、完整性、空目录条件和一次性修复次数。目标 Windows 设备覆盖更新后的启动仍待现场确认。

### 已发布版本的本地记录恢复

状态：待单独核对。1.31 防止继续回滚，但不会自动恢复已经被旧版本覆盖的本地记录。恢复前必须保留当前 `data/`、旧恢复备份和云端同步资产，并先完成数据差异核对。

### v1.34 发布后核查

状态：GitHub 发布与远端资产核对已通过；目标用户设备实测仍待完成，不等于全量验收通过。

- Release `v1.34` 已公开并标记 Latest；Release/tag/正文和 4 个正式附件已回读。
- 安装包、blockmap、Web Demo、`latest.yml` 的远端 SHA-256 与本地构建结果一致；安装包下载端点返回 HTTP 302。
- 自动化检查 37 项通过，类型检查、渲染器构建和 Windows x64 安装包构建通过。
- 仍需在目标 Windows 设备核验覆盖安装后启动、`data/` 和使用统计记录保留、云同步再次连接/同步、托盘行为与更新失败回退；现场核验前均保持“待真实验收”。
- 详细证据见 `版本记录/18-1.34界面同步与更新回退修复.txt` 与 `1.34/文档/发布执行计划.md`。

### v1.34 目标设备再次发生启动崩溃（v1.35 修复中）

2026-09-23 现场截图与只读核查确认：`D:\APP\cherry 网关\cherry-ai-connect\data` 不存在；用户目录中的恢复指针指向 1.32 备份，已记录 `restoredAt` 和 `recoveryRepairAt`；1.32 备份仍在，包含网关关键文件及 `usage.db`。1.34 的 `electron/main.js` 在模块初始化阶段直接调用恢复函数，而恢复函数对“已消费、已修复、当前数据缺失”抛出 `update_recovery_data_missing_after_consumption`，造成主进程未捕获异常。此前 1.32/1.33 单测通过并不能替代这台目标设备的覆盖更新验收。

修复要求：将正式版数据移出安装器会替换的程序目录；完整旧数据只复制迁移，不覆盖现有数据；失去当前数据但有旧备份时向用户说明备份版本与可能缺失的后续记录，仅经明确选择后恢复；无可用备份或部分数据时保护性停止。发布前必须按上述现场状态回归，核对启动、连续重启、统计、客户端 Key、同步凭证与备份留存。验收证据和未完成项记入 `版本记录/19-1.35启动恢复与数据目录保护.txt`。

v1.35 发布前复核：已将统计库缺失或空文件纳入保护性停止，旧指针已消费时仍核查并按同设备身份补回缺失的云同步凭证；恢复复制先写临时目录再切换，指针替换保留上一份副本。44 项自动化检查和隔离打包启动保护提示通过；目标设备真实恢复、统计连续性和云同步仍须单独实测，未实测不得标记通过。

v1.35 发布后核查：GitHub Latest、四个附件状态/大小/SHA-256 与安装包下载入口已验证；v1.34 故障 Release 转为 Draft，公开安装包直链返回 404。目标设备未安装新版本，现有数据与备份仍原样保留；现场恢复、完整统计与真实同步仍是 P0 待验收项。

## 强制执行规则

1. 本文件优先于普通视觉、文案和低风险交互问题。
2. 任何 P0 项没有证据，不得写“已完成”或“已发布”。
3. 发现本地数据、同步或加密边界异常时，先停止发布和自动清理，再保留现场并记录证据。
4. 每次发布结束后，把新增严重问题和核查结果写回本文件或对应版本记录。
