======================================================================
一、1.00 正式版的产品定位
======================================================================

Cherry Gateway 1.00 是一个运行在 Windows 本机上的多线路 AI API 网关。
它为 Cherry Studio、其他 OpenAI 兼容客户端和本地应用提供统一的本地 API 地址，
再根据客户端 Key 绑定的线路、模型和思考强度，把请求转发到用户配置的中转站。

1.00 的核心目标：

1. 本地网关稳定运行，支持网关重置、端口随机化、托盘运行和开机启动。
2. 一个客户端 Key 只能绑定一条中转线路，客户端 Key 可编辑、停用和永久删除。
3. 支持 low、medium、high、xhigh、max 五档思考强度，并真实透传给上游。
4. 支持线路检测、模型目录同步、模型搜索和按线路分组展示。
5. 支持实时使用记录、半年趋势和没有时间限制的永久累计 Token 统计。
6. 使用 GitHub 作为默认同步和备份渠道，但不把同步数据写入普通 Git 文件历史。
7. 使用 GitHub Release 的附件作为云端同步文件；每次只保留最新附件。
8. Google Drive、OneDrive 作为可选云盘适配器，不影响 GitHub 主流程。
9. 中转站 Key 与使用数据分开；客户端 Key 永远不上传。
10. 中英文界面完整，所有核心按钮、状态、错误、空状态和文档均有对应翻译。
11. 安装包、托盘图标、底部菜单图标和应用图标使用同一套产品图标资源。
12. 交付给测试人员的文档可以独立说明安装、配置、同步、测试和故障排查。

1.00 的正式版边界：

- 本地网关业务必须可脱离云同步独立运行。
- GitHub 授权失败不能阻止 Cherry Gateway 本地转发。
- Google Drive 或 OneDrive 未配置时不显示阻塞性错误。
- 云同步发生异常时，不能删除本地线路、客户端 Key、统计或历史数据。
- 自动同步不能上传聊天正文、提示词、回答内容或客户端 Key。

======================================================================
三、GitHub 云端组织方式
======================================================================

每个 GitHub 用户只创建一个专用私有仓库和一个固定 Release：

```text
仓库：cherry-gateway-sync-<用户标识>
Release：Cherry Gateway Sync
```

不创建：

- 每台设备一个仓库；
- 每条线路一个仓库；
- 每个月一个仓库；
- 每次同步一个 Release。

这样可以把用户的数据集中在一个位置，同时避免仓库数量失控。

Release 附件不是普通 Git 文件，不会因为每次替换同步数据而创建普通 Git 提交。
同步时采用“先上传、校验、再删除”的方式，避免网络失败导致云端只剩空文件。

附件替换流程：

```text
本地生成新数据
    ↓
压缩
    ↓
必要时加密
    ↓
计算 SHA-256
    ↓
上传新 Release Asset
    ↓
读取并校验新 Asset
    ↓
确认校验成功
    ↓
删除旧 Asset
```

如果程序在删除旧附件前崩溃，下一次同步会发现同一类别存在两个附件，
选择校验正确且 generation 最大的文件，并清理多余附件。

======================================================================
四、云端文件详细设计
======================================================================

所有文件均为 Release Asset。文件名带 generation，是同步代数，不是 Git 提交版本。

一、manifest 文件

文件示例：

```text
manifest-000042.json
```

作用：

- 告诉软件当前同步包包含哪些数据；
- 标记数据格式版本；
- 标记生成设备和同步时间；
- 标记每个文件的大小和 SHA-256；
- 防止下载到未上传完整的附件。

字段设计：

```json
{
  "format": "cherry-gateway-sync",
  "schemaVersion": 1,
  "syncId": "sync_01995f2c-7f5a-7b21-a8d2-6dfc50f4a901",
  "generation": 42,
  "deviceId": "dev_8d7d4c01-8e94-4e1d-bc7d-4e6a31e5b201",
  "createdAtUtc": "2026-09-16T10:30:00.000Z",
  "displayTimezone": "Asia/Shanghai",
  "state": "committed",
  "files": {
    "summary": {
      "assetName": "summary-000042.json.gz",
      "sha256": "...",
      "size": 1234
    },
    "config": {
      "assetName": "config-000042.json.gz",
      "sha256": "...",
      "size": 2345
    },
    "vault": {
      "assetName": "vault-000042.enc",
      "sha256": "...",
      "size": 3456
    }
  },
  "retention": {
    "detailQuotaBytes": 5368709120,
    "detailMaxBytes": 8589934592,
    "prunedBeforeUtc": null
  }
}
```

manifest 上传顺序必须最后完成。只有 `state=committed` 的 manifest 才能被读取。

二、summary 文件

文件示例：

```text
summary-000042.json.gz
```

作用：

- 保存永久累计使用量；
- 保存按设备累计总账；
- 保存按模型、线路、日期的汇总；
- 保存缓存命中统计；
- 为统计页提供快速读取，不必每次扫描所有明细。

字段设计：

```json
{
  "schemaVersion": 1,
  "updatedAtUtc": "2026-09-16T10:30:00.000Z",
  "lifetime": {
    "requests": 1842,
    "successRequests": 1801,
    "failedRequests": 41,
    "inputTokens": 1250340,
    "outputTokens": 382910,
    "cacheReadTokens": 740220,
    "cacheWriteTokens": 1200,
    "totalTokens": 2364670
  },
  "deviceTotals": {
    "dev_8d7d4c01": {
      "requests": 1842,
      "totalTokens": 2364670,
      "lastSequence": 1842,
      "lastEventAtUtc": "2026-09-16T10:30:00.000Z"
    }
  },
  "byDay": {},
  "byWeek": {},
  "byMonth": {},
  "byModel": {},
  "byRoute": {}
}
```

永久总账不能因为删除旧明细、重启、重置网关、换语言或更换端口而减少。

三、config 文件

文件示例：

```text
config-000042.json.gz
```

只保存非敏感配置：

- 线路代号；
- 线路显示名称；
- API URL；
- 线路启用状态；
- 模型目录的非敏感元数据；
- 最近检测时间、状态和延迟；
- 客户端 Key 的名称；
- 客户端 Key 绑定的线路 ID；
- 思考强度；
- 客户端 Key 创建时间和启用状态；
- 用户是否自定义名称；
- 界面语言和同步设置。

不保存：

- 上游 API Key；
- 完整客户端 Key；
- Authorization；
- 聊天正文；
- 提示词和模型回答。

客户端 Key 的本地编号可以同步，但完整 Key 只能留在本机。

四、vault 文件

文件示例：

```text
vault-000042.enc
```

只有用户主动设置独立密码后，才允许生成并上传 vault。

处理顺序：

```text
中转站配置 JSON
    ↓
gzip 压缩
    ↓
scrypt 派生加密密钥
    ↓
AES-256-GCM 加密
    ↓
写入 salt、nonce、tag、ciphertext
    ↓
上传 vault.enc
```

示例外层格式：

```json
{
  "format": "cherry-vault",
  "version": 1,
  "kdf": "scrypt",
  "salt": "base64...",
  "nonce": "base64...",
  "authTag": "base64...",
  "ciphertext": "base64..."
}
```

独立密码不上传云端。恢复码只在首次设置密码时展示一次，也不上传云端。
用户忘记密码时使用恢复码恢复；密码和恢复码同时丢失时，云端 vault 无法解密，
但历史统计仍然可以同步，本机未损坏的配置仍然保留。

五、usage 明细文件

文件示例：

```text
usage-deviceA-202609-part01.json.gz
```

使用 JSONL 格式，一行一条记录，上传前 gzip 压缩。

单条记录设计：

```json
{
  "eventId": "evt_01995f2c-7f5a-7b21-a8d2-6dfc50f4a901",
  "deviceId": "dev_8d7d4c01-8e94-4e1d-bc7d-4e6a31e5b201",
  "sequence": 1842,
  "occurredAtUtc": "2026-09-16T10:30:00.000Z",
  "routeId": "route_4routerai",
  "routeName": "4RouterAI",
  "model": "gpt-5.6-luna",
  "thinkingLevel": "high",
  "endpoint": "/v1/responses",
  "stream": false,
  "inputTokens": 2450,
  "outputTokens": 862,
  "cacheReadTokens": 1200,
  "cacheWriteTokens": 0,
  "totalTokens": 4512,
  "latencyMs": 3260,
  "ttftMs": null,
  "status": 200,
  "success": true
}
```

禁止字段：

- prompt；
- response；
- messages；
- system prompt；
- 完整客户端 Key；
- 上游 API Key；
- Authorization；
- Cookie；
- 用户完整 IP。

六、时间规则

所有数据内部使用 UTC ISO 8601：

```text
2026-09-16T10:30:00.000Z
```

界面显示使用：

```text
2026-09-16 18:30:00
UTC+8
```

不能只依赖本机时间判断上传或下载。时间只用于展示和辅助排序，真正判断使用：

- 云端 Asset 的更新时间；
- manifest generation；
- 文件 SHA-256；
- 本地上次同步指纹；
- configRevision；
- eventId 去重。

======================================================================
五、编号和版本规则
======================================================================

1. deviceId

首次运行时随机生成并保存在本机，卸载重装后视为新设备。

格式示例：

```text
dev_8d7d4c01-8e94-4e1d-bc7d-4e6a31e5b201
```

2. eventId

每一条请求记录的全局唯一编号，推荐 UUIDv7。

格式示例：

```text
evt_01995f2c-7f5a-7b21-a8d2-6dfc50f4a901
```

3. sequence

设备本地递增编号，便于检查是否存在断号。sequence 不能替代 eventId。

4. syncId

每次同步操作生成一个新的编号，用于日志和问题排查。

5. routeId

线路创建时生成，线路改名不改变 routeId。

6. clientId

客户端 Key 本机编号，完整客户端 Key 不上传。删除客户端 Key 后，clientId 进入本机删除记录，
防止旧客户端 Key 再次通过缓存认证。

7. configRevision

配置使用逻辑版本号，不直接依赖电脑时间。并发修改时使用：

```text
{ counter, deviceId }
```

相同基础版本上出现两个不同修改时，判定为冲突，不静默覆盖。

8. generation

Release Asset 的同步代数，只表示当前同步包的新旧，不代表 GitHub 提交。

======================================================================
六、同步流程和多设备准确性
======================================================================

一、软件启动

```text
读取本地数据
    ↓
读取 GitHub Release Asset 列表
    ↓
校验 manifest
    ↓
发现云端比本地新：下载并合并
    ↓
本地有新数据：上传合并结果
    ↓
更新本地 lastRemoteFingerprint
```

二、开启同步

```text
读取云端
    ↓
合并本地数据
    ↓
检查配置冲突
    ↓
上传合并结果
    ↓
同步成功后显示“已连接”
```

三、关闭同步

```text
检查待同步队列
    ↓
尝试上传一次
    ↓
成功：关闭同步
失败：保留本地队列并提示“还有数据待同步”
```

关闭同步不能删除本地数据。

四、软件退出

软件退出时尽力执行一次同步。正常关闭窗口不应立即杀掉网关进程，
要先完成短时同步任务，再隐藏到托盘或退出。

如果是断电、任务管理器强制结束或系统崩溃，不能保证最后一次网络上传，
但本地使用记录必须已经先写入磁盘，下次启动继续上传。

五、普通同步

GitHub 默认每 30 分钟检查一次：

- 没有本地变化时不上传；
- 有变化时合并为一次同步包；
- 先上传新附件，再删除旧附件；
- 失败后进入待同步队列；
- 不连续快速重试；
- 可显示上次同步、下次同步和待同步数量。

六、使用记录合并

每台设备只写自己的 usage 文件。

合并规则：

1. 读取所有设备的记录；
2. 以 eventId 建立去重集合；
3. 已存在的 eventId 不重复计入；
4. 新 eventId 追加到统计数据；
5. 每台设备的 lifetime 只取该设备最新总账；
6. 全局 lifetime 等于所有设备最新总账之和；
7. 明细清理不减少 lifetime。

七、配置合并

配置按照对象 ID 合并：

- 不同对象分别合并；
- 同一对象只有一台设备修改时自动采用新版本；
- 同一对象两台设备同时修改时生成冲突；
- 用户选择保留本机、保留云端或手动合并；
- 线路删除和客户端 Key 绑定关系必须再次校验。

八、冲突保护

GitHub Release Asset 没有普通文件接口那样的天然事务锁，所以程序需要本地同步锁：

- 同一进程内同一时间只允许一个上传任务；
- 上传前再次读取远端 Asset 列表；
- 上传失败不删除旧文件；
- 下载时校验 SHA-256；
- 发现多个候选附件时选择已校验、generation 最大的文件；
- 发生并发修改时保存冲突副本，不直接覆盖。

======================================================================
七、容量、压缩和清理策略
======================================================================

一、压缩对象

需要压缩：

- usage 明细；
- summary 统计；
- config 配置；
- vault 加密前的配置内容。

压缩顺序必须是：

```text
原始 JSON
→ gzip
→ 加密（如果需要）
```

不能先加密再压缩，因为加密后的数据通常无法有效压缩。

二、容量规则

- GitHub 明细默认配额：5GB；
- GitHub 明细最大配额：8GB；
- 接近 7GB 时提醒；
- 达到 8GB 时暂停上传明细并提示清理；
- summary 永久保留；
- vault 不参与明细清理；
- 客户端 Key 不上传；
- 清理按照最旧 usage 分片优先；
- 清理前重新计算并保存 lifetime 总账。

5GB 和 8GB 是应用自身的安全阈值，不代表 GitHub 向每个仓库保证分配固定容量。
GitHub 官方建议单仓库控制在 10GB 以内，因此保留安全余量。

三、GitHub 历史处理

Release Asset 不产生普通 Git 提交，但 GitHub 可能有自己的后台保留策略。
程序不自动重写 Git 仓库历史，不执行 force push，不删除用户代码历史。

同步附件的旧版本通过 Release Asset 删除；如果删除失败，保留旧附件并在下次同步重试。

四、明细清理后的数据准确性

明细删除只影响：

- 请求时间线；
- 请求详情；
- 半年以内的折线图明细。

明细删除不影响：

- 永久累计 Token；
- 永久累计请求数；
- 永久成功/失败数量；
- 永久缓存统计；
- 线路累计统计；
- 模型累计统计。

======================================================================
八、GitHub 登录和权限设计
======================================================================

一、登录方式

桌面端使用 GitHub OAuth Device Flow，避免把客户端 Secret 写入 EXE。
用户第一次操作时：

1. 点击“连接 GitHub”；
2. 软件显示 GitHub 验证网址和一次性验证码；
3. 用户在浏览器确认授权；
4. 软件轮询授权状态；
5. 成功后读取 GitHub 用户标识；
6. 查找专用私有仓库；
7. 没有仓库时创建一个；
8. 查找固定 Release；
9. 没有 Release 时创建一个；
10. 开始初始化同步。

二、本地 Token 保存

GitHub access token 不能写入：

- config.json；
- 日志；
- usage.json；
- Release Asset；
- 前端 localStorage。

应保存到 Windows Credential Manager 或 DPAPI 保护的本地凭据存储。

三、权限说明

自动创建私有仓库需要较高权限。程序必须在授权前明确告诉用户：

- 只创建一个 Cherry Gateway 专用私有仓库；
- 不创建其他仓库；
- 不上传聊天内容；
- 不上传客户端 Key；
- 用户可以随时在 GitHub 设置中撤销授权。

如果未来 GitHub App 能提供更细的“只访问指定仓库”权限，应优先迁移到 GitHub App。

四、账户与仓库绑定

本地保存：

```json
{
  "provider": "github",
  "githubUserId": "...",
  "repositoryOwner": "...",
  "repositoryName": "cherry-gateway-sync-...",
  "releaseId": "...",
  "connectedAtUtc": "..."
}
```

不保存 GitHub 密码，只保存安全存储的授权引用。

九、界面和用户操作设计
======================================================================

一、设置页云同步卡片

显示内容：

```text
云同步
GitHub 备份：已开启
连接账户：BFTwarrior
专用仓库：已创建
同步对象：Release 附件
上次同步：2026-09-16 18:30:00
下次同步：29分钟后
待同步数据：0条
```

按钮：

- 连接 GitHub；
- 立即同步；
- 关闭 GitHub 备份；
- 打开 GitHub 仓库；
- 查看同步日志；
- 断开账户。

二、云同步开关规则

开关打开：先拉取、合并、上传一次，成功后显示开启。

开关关闭：先上传一次，成功后显示关闭；失败时保留待同步状态并给出提示。

三、同步状态颜色

- 绿色：已连接、数据已同步；
- 紫色：正在同步；
- 黄色：等待重试或有待同步数据；
- 红色：授权失效、数据校验失败或连续同步失败；
- 灰色：未连接或用户主动关闭。

四、数据安全提示

首次设置独立密码时必须显示：

```text
此密码用于加密中转站 Key。
Cherry Gateway 不保存你的密码。
请同时保存恢复码，密码和恢复码丢失后无法解密云端 Key。
```

五、客户端 Key 页面

客户端 Key 卡片必须提供：

- 复制 Key；
- 复制本地 API 地址；
- 测试连接；
- 编辑；
- 停用/启用；
- 永久删除。

客户端 Key 默认名称等于绑定线路名称。
用户手动改名后，记录 `nameCustomized=true`，之后不再跟随线路名称变化。

十、现有本地数据和升级迁移
======================================================================

1.00 首次启动时检测旧版本数据目录：

```text
%APPDATA%/Cherry Gateway/gateway-data/
```

迁移原则：

1. 迁移前创建本机备份副本；
2. 不删除原始配置；
3. 不覆盖原始 usage；
4. 为旧数据添加 schemaVersion；
5. 保留原有线路、模型、客户端 Key 和思考强度；
6. 客户端 Key 仍然只在本机保存；
7. 未连接 GitHub 时不上传任何数据；
8. 用户完成授权后才执行云端初始化；
9. 迁移失败时回滚到旧数据；
10. 在设置页显示迁移结果。

当前本地 JSON 方案在 1.00 继续保留，不强制引入 SQLite。
只有当单机统计数据规模真正超过 JSON 读写能力时，才在后续版本评估 SQLite 迁移。

13. 停用客户端 Key；
14. 重新启用客户端 Key；

18. 测试 Responses；
19. 测试 Chat Completions；
20. 测试流式和非流式请求。

二、网关和端口

1. 启动网关；
2. 检查 127.0.0.1；
3. 检查端口范围；
4. 执行网关重置；
5. 确认旧地址失效；

三、统计

1. 发送成功请求；
2. 发送失败请求；
3. 检查输入 Token；
4. 检查输出 Token；
5. 检查缓存读写；
6. 检查缓存命中率；
7. 检查 24 小时；
8. 检查 7 天；

15. 检查时间线和详情面板；

四、GitHub 初始化

1. 用户未登录 GitHub；
2. 点击连接 GitHub；
3. 完成设备授权；
4. 自动创建一个私有仓库；
5. 重复操作确认不会创建第二个仓库；
6. 自动创建一个固定 Release；
7. 重复操作确认不会创建第二个 Release；
8. 上传 manifest；
9. 上传 summary；
10. 上传 config；
11. 设置独立密码后上传 vault；
12. 确认客户端 Key 不在任何附件中；
13. 确认聊天正文不在任何附件中。

五、GitHub 同步

1. 本地发送请求；
2. 等待普通同步周期；
3. 检查 Release 附件；
4. 确认新附件上传成功；
5. 确认旧附件被清理；
6. 确认普通仓库没有新增同步提交；
7. 开启同步时立即同步；
8. 关闭同步时立即同步；
9. 启动软件时同步；
10. 关闭软件时尽力同步；
11. 点击立即同步；
12. 无变化时确认不上传；
13. 断网后确认本地数据保留；
14. 恢复网络后确认自动补传。

六、多设备

1. 设备 A 产生 100 条记录；
2. 设备 B 产生 50 条记录；
3. 两台设备分别上传；
4. 第三次同步后总记录为 150 条；
5. 重复下载不重复计算；
6. 同一配置只在一台设备修改时自动合并；
7. 同一配置在两台设备同时修改时弹出冲突；
8. 选择本机版本；
9. 选择云端版本；
10. 检查冲突处理后数据完整。

七、压缩和加密

1. 检查 usage 是 gzip 压缩文件；
2. 检查 summary 可正确解压；
3. 检查 vault 是压缩后加密；
4. 错误密码不能解密 vault；
5. 正确密码可以恢复 vault；
6. 使用恢复码可以恢复；
7. 修改密码后旧 vault 不能被新密码以外的密码读取；
8. 日志不出现明文 Key；
9. Release 附件不出现明文 Key；
10. Release 附件不出现聊天正文。

八、异常和恢复

1. 上传新附件中断；
2. 删除旧附件中断；
3. 下载附件损坏；
4. SHA-256 校验失败；
5. GitHub 返回 401；
6. GitHub 返回 403；
7. GitHub 返回 409；
8. GitHub API 限流；
9. 两台设备同时上传；
10. 软件强制结束；
11. 电脑断电；
12. 重新安装软件；
13. 恢复本地备份；
14. GitHub 仓库被用户删除；
15. Release 被用户删除；
16. GitHub 授权被撤销。

十五、开发注意事项
======================================================================

1. 不允许把真实 API Key 写进源码、示例、测试、日志或文档。
2. 不允许把 GitHub Token 写入 JSON 或前端 localStorage。
3. 不允许把客户端 Key 上传到 GitHub、Google Drive 或 OneDrive。
4. 不允许把聊天正文写入 usage。
5. 不允许用本机时间直接覆盖云端较新配置。
6. 不允许同步时直接覆盖未上传的本地记录。
7. 不允许在删除旧附件前删除新数据。
8. 不允许在同步失败时清空本地待同步队列。
9. 不允许通过 GitHub 普通仓库提交保存高频统计。
10. 不允许自动重写用户的 GitHub 代码仓库历史。
11. 所有永久删除操作必须有明确确认。
12. 所有同步错误必须可读、可重试、可追踪。
13. 所有新数据文件必须带 schemaVersion。
14. 所有云端文件上传前必须执行敏感字段扫描。
15. 正式版代码、测试数据和文档必须保持项目目录内分类整理。
