# Cherry AI Connect 1.23 产品文档：修复与同步规则

更新时间：2026-09-19（UTC+8）　状态：待修复

## 版本目标

修复首次同步显示问题，拆开用量与敏感配置的同步边界，并简化密钥恢复、版本保留和文件命名规则。本版本只处理下列已登记事项，测试期间的新问题自动登记到后续版本。

## 1. 首次同步后中转站 API 不显示（最高优先级）

现象：新设备或空数据首次完成 GitHub 同步后，中转站 API 没有显示；手动创建一条中转站 API 后，已同步的全部 API 才突然出现。

修复要求：首次同步必须一次性读取完整清单，写入线路、模型和绑定关系，完成索引后主动刷新页面状态；不得要求用户先手动创建一条线路。

验收标准：首次同步成功后无需手动创建线路，页面自动显示全部已同步的中转站 API、模型数量、可用状态和绑定关系；刷新、重启和再次同步后结果保持一致。

## 2. 用量同步不得依赖本地保险库

现象：GitHub API 和私有仓库访问正常，但本机 `vault-local-key` 无法解密时，连不需要加密的用量数据也无法同步，界面还可能错误显示为已连接。

修复要求：用量数据作为独立、简单的数据上传，不加密、不依赖 `vault-local-key`；GitHub API 授权后即可同步用量和基础元数据，默认不上传中转站 API。中转站 API 云同步由独立开关控制，只有用户主动开启后才要求创建密码；首次读取到云端中转站 API 时，密码/恢复码提示必须允许关闭。本地保险库暂时不可解锁时，不覆盖、不删除云端上一份敏感配置，也不能把同步状态误报为正常。

验收标准：GitHub API 正常且保险库不可解锁时，用量仍能上传和合并；保险库恢复后，敏感配置可继续同步；更新、重启和重试不会丢失云端敏感配置。

## 3. 密钥显示、恢复和修改规则

本条只针对中转站/上游密钥，不改变“同一设备更新、重启、同步不得刷新客户端 API Key”的既有规则。

- 系统生成的密钥：首次显示一次；允许恢复，但恢复冷却时间为 24 小时。
- 多设备限制：恢复资格绑定同步身份或仓库身份，不能只绑定本地设备；所有设备共享冷却状态，避免每台设备各自重置。
- 用户创建的密钥：允许在设置中修改或轮换，修改前确认，保存后再次验证线路。
- 密钥恢复或修改失败：保留旧密钥和旧配置，不显示“已成功”。
- 加密与解密单独维护为稳定模块，跨版本使用同一兼容协议；修改前必须完成旧数据回读和跨版本测试。

验收标准：同一同步身份在多台设备上不能绕过 24 小时限制；密钥修改后新值可用，旧值按明确规则失效；客户端 API Key 在更新后保持不变。

## 4. 云端版本保留规则

云端只保留两类数据：最近一次有效版本，以及最近 24 小时内受保护的旧版本；成功生成新版本后，删除更早的版本。上传失败时不得删除旧版本或用空数据覆盖旧版本。

验收标准：同步成功后可恢复当前版本和 24 小时内旧版本；超过保护期的更早版本不再保证存在；异常中断不会造成云端空仓或数据消失。

## 5. 文件命名规则

文件名只使用英文前缀、UTC+8 时间到毫秒和序号，按数据类型分组，不把不同数据混在同一命名空间：

`<type>-YYYYMMDDTHHMMSS.mmm+0800-<sequence>`

示例：`data-20260818T234407.087+0800-34`、`usage-20260818T234407.087+0800-34`。固定使用 `data`、`usage`、`manifest`、`vault` 等英文前缀，GitHub 列表中按前缀对齐和区分。

## 6. 同步执行顺序

1. 验证 GitHub 授权和仓库可写性。
2. 读取远端清单，分类处理用量数据与加密敏感配置。
3. 先上传独立用量数据；只有用户开启中转站 API 同步且保险库可解锁时，才处理敏感配置。
4. 校验文件、SHA-256、哈希和版本时间，安装包哈希缺失或不匹配时禁止更新。
5. 所有校验通过后最后提交清单；任一步失败都保留旧版本、记录错误和下次重试时间。

## 故障边界

1.23 不能保证 GitHub、网络或授权服务永远不出错；它保证单个环节失败时不会拖垮全部同步：用量独立完成，敏感配置保留旧版本，清单未提交就不宣称同步成功，并提供重试信息。

## 验收范围

- 空数据新设备首次同步后，全部中转站 API、模型和绑定关系可见。
- 保险库不可解锁时，用量仍可独立同步。
- 多设备不能绕过密钥恢复冷却；用户密钥可修改。
- 云端只保留当前版本和 24 小时保护版本。
- 文件名符合英文前缀、UTC+8 毫秒时间和序号规则。
- 更新、重启和再次同步不刷新客户端 API Key。

## 7. 首页文字排版和用词

问题：主宣传区域的说明文字被挤成第二行只有一个字，视觉不平衡；“本地连接脉搏”属于生硬的机翻表达，用户难以理解。

要求：重新设置文字最大宽度、断行和字号，禁止出现孤立单字；将“连接脉搏”改为用户能直接理解的“本地连接状态”或同义中文，并统一检查中文和英文界面。

验收：默认窗口、缩放窗口和英文界面下均不出现孤行、溢出或含义不清的状态文案。

## 8. 云同步独立工作区

问题：云同步目前嵌在设置页面中，信息和操作被挤在一张卡片里，不利于查看状态和排查失败。

要求：在主导航增加独立“云同步”工作区，重新设计页面结构，至少包含同步状态、立即同步、上次/下次同步、仓库信息、数据保护、版本记录和失败原因；设置页只保留本机设置，不再承载云同步主流程。

验收：用户无需进入设置即可完成同步、查看进度、区分成功/部分成功/失败，并能看到下一次重试时间。

## 9. 语言入口和设置页排版

问题：语言选择在设置页占用一整行，删除后会留下空白和不平衡布局。

要求：从设置页移除“界面语言”卡片；在顶部语言按钮中点击后展开语言选项卡，保持当前语言、切换入口和即时生效；设置页重新排版剩余内容，不保留空横条。

验收：中文/English 切换无需进入设置，弹出选项位置稳定；设置页在默认窗口下无大面积空白、错位或卡片高度失衡。

## 10. 图标统一与高级视觉风格

问题：同一页面的中心线性图标颜色不一致，部分仍是紫色、蓝色或绿色，整体质感不统一；各卡片原有底色可以保留。

要求：保留各图标容器原有的紫色、蓝色、绿色和棕色底色，只把中心线性图标统一为金色；统一图标尺寸、描边和内边距，状态变化继续由文字、状态点或标签表达。

验收：首页、云同步、设置、线路、Key 和状态卡片中的中心图标均为金色，底色层次仍然保留；新增图标必须通过共享 `Icon` 组件和本条颜色规则的回归检查，中文和英文界面一致。

## 11. 更新后启动设置被重置

问题：软件更新后，“自动开机”和“开机隐藏”会出现被取消勾选的情况，导致用户的桌面行为设置丢失。

要求：更新前备份并迁移启动设置；覆盖更新、重启和首次启动后必须恢复原值，不得用默认值覆盖用户选择。设置缺失时才使用默认值，并记录迁移结果。

验收：分别测试两项全选、全不选和只选一项的升级场景；更新后设置值保持一致，Windows 启动、隐藏到托盘和窗口关闭行为与升级前一致。

## 12. 一级卡片边框一致性

问题：总览中并列卡片的边框规则不一致，连接状态使用金色边框，而客户端路由及其他一级卡片仍使用普通边框。

要求：所有一级内容卡片统一使用同一套淡金色边框；内部模块和错误/成功状态可以保留各自的层级或状态边框，但不得让同级卡片出现无规则差异。

验收：总览、线路、模型、客户端 Key、使用统计、云同步和设置页面的一级卡片边框一致；悬浮、错误和选中状态只在交互状态下改变。

## 13. 视觉细节收口

问题：品牌图标、顶部操作区、语言当前值和安全更新卡片的视觉层级仍不统一，设置页更新卡片上方出现大面积空白。

要求：品牌标记使用与其他紫色图标一致的紫色底、单条 1px 金色边框和白色中心图标并视觉居中，不叠加金色外圈；右上角各个操作控件分别使用与一级卡片相同的 1px 淡金边框，不增加包住它们的外层框；语言按钮显示当前语言并点击展开选项；更新卡片移入左列并压缩为紧凑两列版本信息布局。

验收：总览和设置页在中文/英文、默认窗口和缩放窗口下均无空白失衡、当前语言显示错误或品牌标记颜色偏离规范。

## 14. 全局卡片交互层级

问题：普通卡片、悬停卡片和选中工作台的边框规则混用，悬停后的紫边反而削弱了金边代表的高级感；部分小卡片和低频页面容易漏掉统一规则。

要求：普通态使用稳定的紫色边框和深色底；悬停/键盘聚焦时使用同一条细淡金边、极淡金色内侧光和 1px 轻微上浮；选中导航使用稳定的淡金边和淡金内填充但不上浮；禁用、成功、错误和加载状态继续使用对应语义色，不被金色覆盖。总览、中转站线路、模型目录、客户端 Key、使用统计、云同步、设置，以及顶部控件、侧栏状态、空状态、错误状态和实时记录都必须经过同一套视觉回归检查。总览最大的“本地连接”欢迎区是唯一固定金边例外：始终带细金边，不响应悬停动画，不改变内部背景。

验收：逐页核对普通态、鼠标悬停、键盘聚焦、选中、禁用、错误、空数据、加载和窄窗口状态；额外确认总览欢迎区始终金边且悬停前后不位移、不变色；新增卡片或图标必须复用共享规则，不能只修当前截图中的元素。

## 统一验收范围

- 默认窗口、窄窗口、最大化、缩放和中文/英文界面。
- 首次安装、覆盖更新、重启和异常退出后重新启动。
- 云同步成功、部分成功、网络超时、授权失败和重试状态。
- 不得因本版 UI 调整改变数据、客户端 API Key 或同步安全规则。

## 不在 1.23 处理

测试期间发现的其他问题只登记到后续版本，不在本版顺手修改；未有实际测试证据的项目标记为“待验收”。
